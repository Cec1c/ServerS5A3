# 道具动作成功回包：结果、槽位、列表与动作号

本候选修正既有伤害字体道具（action 162）和任务完成券（action 167）的 class1/op515 成功回包。当前 EXE SHA-256 为 `8bf1d39df74c6ca6fdbea30a95e055398aad9729305c7ea510ce01af2141e387`。不更改任务结算、用券资格、扣券数量，也不把本项计为新版裂缝追加券已接线。

## 当前 EXE 的读取证据

- `0x2523c9c..0x2523cf6` 按 packet class 分发；class1 在 `0x2523d00` 用 byte reader `0x37e82e0` 消费 body 首字节作为结果。非零成功时不会再读错误码；零结果才可能在 `0x2523d54` 读错误字节。
- `0x2523e4f..0x2523e5a` 将结果/错误参数传给 `0x251e1e0`。后者从已注册表取 handler，`0x251e260..0x251e26c` 依次传入 opcode、结果、错误、注册上下文。
- op515 在 `0x4480670` 注册 handler `0x24f3580`。成功路径 `0x24f35cf/0x24f35dd/0x24f35e9` 读 u16 槽位、u8 列表、u32 动作。列表与槽位用于定位背包物品；动作值传给 `0x24f1bf0` 并作为 `0x24ef3c0` 的分发键。
- 因此旧 body `01 57 00 00 00 03 00 00 00 01`（槽87、余3）在客户端读成 action 768，而非任务完成券的167。候选为 `01 57 00 00 a7 00 00 00`。字体券相应为 action162。

离线模拟执行上述真实 x86 片段，只有 packet reader 与已核实的注册表查询替换为测试桩；覆盖 action162/167、余量0/1/3/70000八种组合，旧包全部读错动作，候选头部全部读对。测试在成功头部读取完成处停止，未运行原生UI，也未证明所有间接回调的尾部读取行为。原始剩余数量字段没有当前客户端读取依据，不再放入动作字段；后续专属动作若有附加payload，必须独立核实。

## 槽位刷新与边界

真正消耗后仍由现有op14权威槽位刷新下发余量。任务完成券无可完成任务时不扣券，但成功回调可能先改变客户端本地物品，因此补发未变化槽位的op14；保持ACK先、权威槽位随后。失败路径不在本候选中改动。

新的字段回归在9de2ecb上两项均失败，修正后通过。既有处理器测试继续校验真实持久扣券与字体归属。完整验证结果另记。本候选未部署，客户端显示与用券实机验收仍开放；追加裂缝次数券的动作号、使用条件及动作回调尚未接线。
