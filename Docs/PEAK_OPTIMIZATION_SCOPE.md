# 高峰优化的缓存与关系表采用范围

本批采用可保持当前持久化、恢复和客户端语义的窄读、差量写、不可变读取视图及请求内复用。外观跨请求整包缓存、公会全量关系表迁移、拍卖权威表迁移及定时历史裁剪本批不采用。以下是针对现有实现的采用评估，不是这些架构永远无效的结论，也不表示当前仍存在的锁与完整写入已经消失。

## 外观：依赖校验的成本和编码的收益分开判断

`remote_actor_equipment_snapshot.go` 已将一次远端角色投影的装备读取固定在请求上下文；此前六轮投影中的 actor 加载从 18 次降为 12 次，receiver 仍为 6 次，帧体相同。该上下文不会作为下一请求的外观缓存。

完整外观不只取决于换装、时装、名字和等级。当前生产者还读取或编码：

- 角色持久状态中的婚姻、职业经验、克隆称号、名称装饰及到期时间；时间到期不需要新的写入事件。
- 技能树、当前装备宠物、宠物名字与显示状态、账号冒险团、公会成员资格与标记。公会有精确指纹，其他全部来源尚无覆盖所有写者的共同版本。
- 接收方已提交的频道、路由、角色绑定代次、当前队伍显示模式和运行时 HP。发送前仍须复核身份和投影资格。

具体生产者见 `current_actor_mode0_appearance_body.go`、`game_select_scene_object_projection.go`、`character_scene_object_tail.go`、`current_equipped_creature.go`、`guild_scene.go` 和 `online_player_manager.go`。

对三类替代方案分别作如下决定：

| 方案 | 可以解决的部分 | 本批决定及理由 |
| --- | --- | --- |
| 完整内容键缓存，先重新取得权威来源，再复用编码 | 可避免部分重复编码；接收方与 HP 在私有副本上覆盖 | 不采用。保留读取才能得到内容键，因此不能提供原建议的 0～1 SQL；编码节约的量级见下文，尚无其为高峰主要耗时的证据。 |
| 持久化依赖版本 + 到期边界 + 接收方/运行时覆盖 | 设计正确时可减少跨请求读取 | 本批不新增。须覆盖 Character/Equipment/Skill/Pet/Account、公会、全部合法写入口、事务回滚与源缺失，并在旧写者/回退时保持版本有效。这是新的跨仓储合同；没有完整实现或收益实测，不能把四事件 epoch 当成已实现替代。 |
| 仅进程内事件失效或短 TTL | 对已知本进程事件容易更新 | 不采用。不能发现不发本地事件的合法持久写入、到期和跨来源改变；TTL 也不能代替身份与资格复核。 |

隔离 Linux 使用真实 mode0 生产者，保持名字、等级和装备固定，分别改变婚姻房屋点数、职业、宠物名、公会标记、冒险团名、接收方频道，六项均改变帧体。现有换装、卸宠物、称号刷新用例也通过。

同一合成角色，三轮固定顺序基准：现编码为 4231～4448 ns/op、约 4584 B/op、53 allocations；已经有效的缓存复制为 144.6～156.1 ns/op、480 B/op、1 allocation。理想复制不含版本查询、同步、失效、mode1、网络或 SQL；它只衡量编码部分，不能换算成整服改善倍数。若后续实际剖析显示序列化分配成为显著负担，可再针对完整内容键或安全子结构缓存评估。

## 公会：保留权威事务，采用精确指纹与读取视图

登记的 35 个公会查询/路由调用点中，34 个已转为不可变视图或适配器，一个周期采样保留完整读。持久指纹候选由实际来源更新维护，正常命中不在每次读取重算整个 JSON 的 SHA；缺失边表等情况仍有精确来源回退。显式维护、旧写者、等时间更新、删除及回退的资格已有独立验证，正式安装另行记录。

`guild_presence.go` 在运行时锁之外持久化规范角色的观察事件，提交后才投递成员刷新；慢成员的查询/回包不再持有其他成员的登录退出 ACK。`guild/presence.go` 的 LastOnlineAt 同时更新排行在线区间，不能当作可随意延后或丢失的显示字段。`guild_monster_experience.go` 使用只读权益视图；这不意味着所有击杀链路均无写入。

完整 `Registry.Save` 和 `WithinGuild` 的持久行锁仍存在。关系表能进一步缩小成员更新范围，但拆出 LastOnlineAt 必须同时迁移排行时间桶、成员资格、事务与旧版回退数据；只在内存延后写入会改变现有持久语义。仅新增关系型只读副本又会保留原全量写入并增加同步工作，无法单凭表名消除该锁。

本批选择已验证的读取视图和持久指纹，不迁移公会写入权威。尚无应用这些读取优化之后的高峰写锁耗时证据，不能宣称全量拆表已经有净收益，也不构造未测量的收益数字。后续若生产剖析明确指向这些权威写事务，再以保持排行/资产/旧写者合同的具体设计重新评估。

## 拍卖：缩小现有行存储的读取，保留结算与历史

拍卖数据当前已经存为 inventory 的槽位和附属行；虚拟 escrow 同时持有资产、出价、退款、邮件 outbox 和重放状态。换成独立商品表本身不会消除这些原子性要求。

普通拍卖新增单个非零物品 ID 的 `InventorySlotItemPrefixReader` 查询。重复 ID 归一化，零值继续忽略；多物品或无筛选使用 listing 前缀，不支持窄接口的适配器保留原读取。排序、过期判断、损坏行排除、分页调用方和错误传播保持。查询失败不会自动扩大读取。

金币寄售 listing/sold 前缀及单物品读取、普通成交均价的物品/历史前缀读取已经采用。真实 MariaDB 对该通用窄接口的参数插值两档及范围结果已有验证，本次未改 SQL 实现。均价只取近期样本不等于可以删除完整用户成交历史和资产恢复回执。

`auction_read_response.go` 已将完成的回包移出 `auctionMu`。准备查询还可能恢复本人到期商品、维护寄售资产并写入会话搜索状态，不能把整段锁直接删除。独立索引表与会话分页快照可以另作设计，但需要维护当前物品分类来源、已售/到期失效、结算复核和旧版写入兼容。固定 1～3 秒快照不能直接替代这些合同。

本批采用普通拍卖最后一处单物品窄读，不新增权威迁表、TTL 搜索缓存、历史裁剪或归档定时。保留所有资产与恢复来源；生产验收继续观察高峰搜索、交易和多人互动的实际延迟。

## 验证范围

本次实际隔离 Linux 11 个主测试、36 个通过节点，零失败、零跳过；覆盖普通拍卖窄读/兼容读取、错误不回退、分类与分页、装备/宠物/称号新状态以及外观依赖反例。编码基准为本地隔离探针，不加入产品测试树或生产程序。相关 vet/list、依赖边界及完整 Linux 正式程序构建通过；未修改的依赖校验与 SQL 窄接口复用既有证据。

此文只固定本批采用范围，不表示源码已贡献或生产已部署。最终累计、准备、独立审查、正式部署、运行核验及玩家验收分别留存结果。
