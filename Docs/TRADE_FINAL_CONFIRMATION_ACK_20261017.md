# 最终确认应答失败时清理交易

双方最终确认时，旧 `handleOnlineItemTradeState` 在互斥锁内先设置 `trade.committing=true`，随后发送当前确认者的成功 ACK，发送成功后才调用资产交换。如果该 ACK 写失败，函数直接返回，交易仍留在两人的索引里且一直为 committing，后续确认、改挂单和取回被拒绝。本项修复是失败路径清理，不涉及未经确认的客户端字段。

新实现仅在双方已最终确认且该 ACK 失败时，调用既有取消路径：清理双方交易索引，尝试向双方发送各自挂单的取消映射，再返回原始写入错误。资产交换尚未发生，不扣晶体、金币或物品，不创建完成回执。之后迟到确认继续走原无交易拒绝，不能把取消的交易再提交。其它确认状态和已经提交后的逐收件人通知隔离保持。

生产状态链回归覆盖挂单者最后确认、接收者最后确认两种顺序。旧实现两种都失败，均留下 committing 交易；新实现两种通过，健康对方收到一次取消、没有完成通知，双方交易索引清空，后续重试不扣源账号的5000晶体，也不向接收账号增发。原9个提交后完成/金币/列表错误注入场景同时通过。本测试使用内存仓储和可注入连接，不是用户现场或GUI。

本轮仍沿原 !72，未部署。本修复不能替代数量上限、对方挂单显示和闪退三个症状的实机验收。R53已证NOTI8短包需要的尾部时间字段，本轮进一步发现相同时间setter同时由NOTI7邀请与NOTI8回应调用；当前代码和本机参考都不足以证明它对应账号还是角色的哪一种业务时间，仍不猜填now、0或CreatedAt。新取得的静态指令与旧叶隔离执行证据只用于约束下一步，不宣称已完整修好握手。
