## 1. 线协议（当前客户端 DNF.exe 8bf1d39df74c6ca6fdbea30a95e055398aad9729305c7ea510ce01af2141e387）

C2S 438（0x1b6），发送端 0x25fae0c/0x25fae16 开包后写序：

| 字段 | 写入点 | writer |
| --- | --- | --- |
| u8 list | 0x25fae4d | 0x374f390 |
| u16 slot | 0x25fae5a | 0x374f3c0 |
| u32 itemTemplateID | 0x25fae67 | 0x374f3f0 |
| u16 materialSlot | 0x25fae77 | 0x374f3c0 |
| u32 名字长度 + 名字字节 | 0x25faebe | 0x374f550 → 0x374f4c0（长度前缀、无 NUL） |
| u8 confirmation | 0x25faece | 0x374f390（来自发送函数参数 [ebp+0xc]） |

现场样例（main slot 9、item 101011368、材料槽 121、两字节名字、confirmation 0）：
`00 0900 a84f0506 7900 02000000 ced0 00`。

class1 438 回包：注册 0x447a740（push 0x1b6 → 0x251e1c0 → 0x2524210/0x25242a0），回调 0x24836b0。
回调先 `cmp byte ptr [ebp+0xc], 0; je 0x2483b60`（成功字节由调度器消费），成功时按序读
u16 materialSlot / u32 materialRemaining / u8 oldLevel / u8 outcome / u8 newLevel / u8 targetList / u16 targetSlot
（0x2483751..0x24837b6），即回包体 13 字节；outcome 0 = 成功、1 = 掷点失败。
失败走 0x2483b60：先 0x12030a0 复位锻造 UI，再按错误码查表显示消息（错误码来自调度器参数 [ebp+0x10]）。
class0 438（0x200e590）是另一条只读 u16 的通知，与本族无关，不能当锻造 ACK。

## 2. 真实 PVF 参数（forge-client-evidence/real-pvf.txt；同一份运行时 Script.pvf，SHA256 369d072b82c715aea4e02813d89ad9225686983e147bc7be0ee0cae2e296bb06）

- `etc/upgrade_separate.etc`：`[separate upgrade max]` = **8**；`[table]` **10 档 × 4 个数**（档位 = 序号+1、第 3 个 = 10000 基成功率、第 4 个 = 材料倍率）；`[item weights by grade]` = 三元组（**grade**、材料模板 **3326**、基础数量，真档 1..25）；`[item weights by rarity]` = 7 个数（0.40 0.70 1 1.25 1.40 1.10 1.30）。
- 参考实现 `Game/Inventory/Services/InventorySeparateUpgradeService.cs`（A21，无 portable 实现，不盲搬）：
  - 普通锻造（:175-270）：目标必须是装备、模板匹配、未上资产锁、`EquipmentTypeInfo.IsWeapon`、耐久等于 PVF 元数据；`oldLevel >= MaxLevel` 拒绝；取 `[table]` 的 **oldLevel+1** 档；材料消耗 `max(1, int(BaseCount × ItemWeightsByRarity[rarity] × level.MaterialWeight + 1e-7))`；材料槽必须是对应模板的堆叠品且数量足够；掷点 `roll ∈ [0,9999]`，`succeeded = roll < level.SuccessWeight`；成功才把等级写成 oldLevel+1；材料已扣而目标写入失败时回滚材料（同一事务内显式补偿）。
  - 券路径（:60-160）：材料槽放券（数量 ≥ 1、堆叠、模板匹配）；`succeeded = roll < ticket.SuccessWeight`；成功 → 目标等级 = `ticket.TargetLevel`（`IsAdditional` 时 = oldLevel + TargetLevel，受 ApplyValue 上限约束）；失败仅在 `FailureDecrementLevel > 0` 时掉级（幸运锻造券为 0 → 保持原等级）。
- 券参数与目标白名单：`tickets.txt` 只是全部 stackable 的 `[reinforcement usable item list]` 扫描（42 KB，CP936）；每个券的 `[action type]`/参数仍需按 stk 逐件 dump 后才能实现（见第 5 节）。
- 便携式锻造炉 10164035（`stackable/10164001/10164035.stk`）：`[action type] = [portable genuine damage upgrade upgrede]`，说明文字明确「使用后可以对装备进行 1 次锻造；锻造时不消耗强烈的气息」→ 消耗炉子本身、不消耗 3326；`[need material] 10164052 200` 是购买/兑换要求，不是锻造消耗。

### 4.3 领域写侧

`modules/dnf/inventory/owner_separate_upgrade.go`：一个**角色物品事务**内完成材料消耗与锻造等级写入。

- 落点：**0x77 行的 0x57 + Extra `byte_57`/`value_57`**（与 gmtool ITEMCFG-D3 同口径），
  0x58/0x59 与其它 Extra 键一个字节都不动。
- 目标容器：主背包 list 0 与穿戴 list 3（装备聚合）；两者都从本角色自己的权威记录读，
  目标归属因此由记录归属保证。
- 校验（每条都有具名 `RejectionReason`）：目标存在 / `item_kind`=equipment / 模板一致 /
  资产锁 / 武器（`[equipment type]`=weapon）/ 实例耐久 = PVF `[durability]`（满耐久）/
  等级 < `[separate upgrade max]` / 品级材料规则存在 / 稀有度权重存在 / 材料模板与数量 /
  券白名单 / additional 券的起始等级上界 /
  耗材声明的 `[check usable itemlevel]` 窗口（目标装备的 `[minimum level]` 必须落在窗口内）。
- 掷点满值 **10000**；普通与便携档失败只扣材料、等级不变；券档失败仅在 `FailureDecrementLevel>0` 时掉级。
- 错误码取厂商同族实现 `SeparateUpgradeResult.Error*`：4 无效目标 / 7 耐久 / 13 不支持 /
  17 材料提交 / 19 非武器与等级窗口限制 / 22 材料不合法 / 95 上限。这 7 个码已在当前 EXE 的
  438 失败回调上**逐码核对**（见 §4.6），全部命中专用文案槽。校验类与存储类失败都回失败体
  让 UI 结束（复位 UI 无条件先执行）；事务回滚保证资产不动。
- 逐槽 op14 只覆盖 list 0（材料槽 + 主背包目标）；穿戴目标由 ACK 自带
  `targetList/targetSlot/newLevel` 让客户端就地更新（list-3 单行 op14 在本仓既有结论里是"不可用/已抑制"）。

### 4.6 438 失败码在当前 EXE 上的逐码核对（2026-10-14 审查补充）

当前客户端 DNF.exe 8bf1d39d…（SHA256，size 111767552，image base 0x400000）。失败回调
0x2483b60 的开头 13 个字节是：

    6a 00 6a 00 6a 00 6a 04 e8 33 f5 d7 fe 0f b6 75 10
    push 0 / push 0 / push 0 / push 4 / call 0x12030a0   ← 无条件复位锻造 UI
    movzx esi, byte[ebp+0x10]                            ← 之后才读错误码

随后 `81 fe d6 00 00 00`（cmp esi,0xd6）+ `0f 87 …`（ja 0x2483c23）分流；码 ≤ 0xd6 走
`0f b6 8e 38 3d 48 02`（字节索引表 @0x2483d38）+ `ff 24 8d 0c 3d 48 02`（11 槽跳转表 @0x2483d0c）。
另有 `0f 85 d3 00 00 00`（jne 0x2483c5f）= 一道前置闸门（0x35ca060）：闸门为真时**跳过文案显示**。

实测（本机读表；脚本与原始输出在 E:/90/_forging-scratch/forgeerr/main.go → forge-error-table.txt）：

| 错误码 | 槽 | 跳转目标 | 文案键 |
| --- | --- | --- | --- |
| 4 | 1 | 0x2483a1c | 0x67a |
| 7 | 2 | 0x2483bf0 | 0x4e20 |
| 10 | 3 | 0x2483bba | 0x67c |
| 13 / 95 | 4 | 0x2483bdf | 0x676 |
| 17 | 5 | 0x2483ba6 | 0x8904 |
| 19 | 6 | 0x2483bce | 0x6a1a |
| 22 | 7 | 0x2483b4c | 0x67d |
| 175 | 8 | 0x2483c01 | 0x5338 |
| 214 | 9 | 0x2483c12 | 0xa4f8 |
| 0 / 118 | 0 | 0x2483c5f | 不显示（直接到函数出口） |
| 其余 203 个码 + 所有 > 0xd6 | 10 | 0x2483c23 | default 分支：文案键 0x67e + 码 |

结论：本实现用的 4/7/13/17/19/22/95 **全部命中专用槽**（没有一个是走 default 的），与厂商同族
`SeparateUpgradeResult.Error*` 的语义一一对应。但"任何码都会显示某句文案"**不成立**（0/118 不显示，
且闸门可抑制显示）；能保证的是**复位 UI 无条件先执行** —— 只要回了失败体，现场"窗口关不掉"就不会再发生。
文案键对应的字串没有在本树里解析（客户端字符串是打包存储），这里只记录命中的键。

### 4.7 耗材的 `[check usable itemlevel]` 窗口（2026-10-14 审查补充）

该段在真档只出现在**耗材**上（真档 Script.pvf 实测 315 个 stackable 带这一段；125 张锻造券与
3 张幸运锻造券**都不带**，交集为 0）：

- 便携式锻造炉 10164035 = `1 90`；同族 10090052 = `1 85`、10094127 = `1 86`；
- 同族 1阶..5阶强化器 = `1 29` / `30 39` / `40 49` / `50 59` / `60 69`（五段窗口，与名字的 1阶..5阶 对应）；
- 客户端物品名里也逐字写着同一个窗口：`凯丽的强化器 (Lv1~90)` / `一次性增幅器 (Lv1~90)` 对应 `1 90`。

比的是哪一个等级：厂商同族实现比的是**目标装备的 `[minimum level]`**
（`ItemUpgradeRestriction.AllowsItemLevel(context.EquipmentLevel)`，
`context.EquipmentLevel = targetMetadata.MinimumLevel`），不是 `[grade]`、也不是角色等级。
本仓按同一口径执行，并且这个选择在真档上可区分：101040493 的 `[minimum level]` = 90、`[grade]` = 96，
于是 1..90 的炉子放行、1..85 的炉子拒绝（4.4 的真档用例按此断言）。
客户端 UI 侧是否也按同一端拦截仍待原生验收。

失败时按客户端的"限制"码 19 拒绝（§4.6：19 → 槽 6 → 文案键 0x6a1a），材料与等级都不动；
目标 PVF 没写 `[minimum level]` 而耗材写了窗口时**失败关闭**（判不进去）。
