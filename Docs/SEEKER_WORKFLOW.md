# Seeker：研究、方案与执行

Seeker 使用 Astra 研究问题，把已确认的成因和可执行方案写入 `Docs/seeker/`，再将边界清晰的小任务交给 DeepSeek Flash。Seeker 负责关键判断、结果验收和下一项选择。

## 角色

| 角色 | 工作与交付 |
| --- | --- |
| Seeker / Astra | 读取问题与格式状态，核对当前代码和资产，复现，解释成因，拆任务，留方案，验收结果 |
| DeepSeek Flash | 在指定工作树实现一个明确目标，补充有意义的回归，返回简短结果和文件路径；默认 low、一次一个、不嵌套 |
| Helper | 用户指定的同模型、同参数助理；承担复杂调查或难点实现，领取独立问题及文件范围 |
| PVF-Writer | 根据 Seeker 的证据和字段级要求修改 PVF，交付精确差异、输入/输出摘要和验证结果 |
| Syncer | 在本次授权范围内接收候选与依赖，负责源码、资源、玩家通道和运行版本的同步及读回 |

当前任务明确启用这些角色后连续推进，已获授权的步骤无需重复询问。新会话先读取交接，核对用户是否继续该任务；文档本身不创建新的委派、发布或上线授权。

## 推进一项问题

1. **选题。** 读取 BUG 原文及颜色，以未涂色的主线任务为优先队列。涂色表示其他人已完成，默认跳过且不计入本轮成果。记录稳定编号、原文定位与当前状态，合并同一原因的重复反馈。已有修复先核对版本及验收记录。
2. **定位。** 从实际代码、匹配的 PVF、日志和请求/回包建立证据。区分任务条件、剧情/副本状态、客户端消费和资产配置。明确“已证实”与仍需验证的一项关键假设。
3. **形成方案。** 使用 [方案模板](seeker/SOLUTION_TEMPLATE.md)，写目标、基线、成因、关键入口、大致解法、修改范围、测试目标与验收条件。公共技术结论放 `Docs/seeker/`；原始资料与环境定位放 ignored 笔记。
4. **派工。** 交接只发送方案路径、工作树、准确基线、允许修改文件、最小证据和输出位置。执行者自行选择实现细节。需要继续研究协议或业务规则时，由 Seeker 或 Helper 先补足证据。
5. **验收。** 检查 diff、实际执行的测试和关键失败场景。发现新问题时给出一个具体修正目标；同一阻塞连续两次尝试无新证据，收回调查或转 Helper，保留执行产物。
6. **交付。** 记录已实现、自动验证、部署和游戏内验收各自状态。需要 PVF 或同步时交对应角色；依赖 EXE 的发布顺序按仓库规则。完成一项后更新索引并进入下一项。

## 给执行者的话

> 允许失败。按方案尝试解决即可；无法完成时，返回已尝试的方法、失败命令或关键证据、当前 diff，以及需要 Seeker 确认的一个问题。真实失败是有效交付。

交接以结论和行动为主，不复述整个调查，不堆叠防御性语句。保持目标、修改范围与验收条件明确。通常一份方案覆盖一个可以单独验证的结果。

返回格式：`结果：完成 / 部分完成 / 失败`；`修改：文件列表或 patch`；`验证：命令、结果、条件跳过`；`待确认：证据与问题`。完整日志放证据文件，主会话读取摘要后按需打开。

## 工具选择

| 证据需要 | 优先工具 |
| --- | --- |
| 代码、版本及调用链 | rg、Git、仓库已有脚本及测试 |
| BUG 文字与涂色状态 | 浏览器读取原格式、截图；保留原文定位 |
| 任务、物品、地图和 NPC 数据 | 匹配摘要的 PVF 只读工具与索引；写入交 PVF-Writer |
| 原生协议或剧情行为 | 日志、协议探针、公共客户端函数索引；必要时 REA/IDA、Capstone 静态取证 |
| 事务及回归 | Go 定点测试、隔离数据库、真实 PVF 专项；按仓库 AGENTS 完成所需整体验证 |
| 面板协作 | Pebrel Runtime；读取真实身份、cwd 和忙闲状态后定向派工 |

先确认工具当前能力，缺失时使用可核实的替代路径。执行子代理确实使用 `deepseek-flash` 才记录为 DeepSeek；本会话未加载时使用本机已配置的可选 profile，不修改全局模型设置。模型启动细节和面板编号只放本机交接。

## 基线、协作与完成条件

- 公共候选从已核实的公共基线建立；部署候选保留线上累计源码和私有扩展。执行者领取独立工作树及文件范围，共享脏树留给其原拥有者。
- 方案中注明验证对象是本地、隔离库或真实客户端；测试数据有明确来源。条件跳过保留为未验证。
- 公共 Docs 保留成因、算法、协议语义、测试目标和验收步骤；玩家信息、原始报文、私人路径、主机、凭据和面板会话留在 ignored 记录。
- 目标模式使用用户明确给出的范围；余额信息不换算成虚构 token 预算，也不把花完余额设为目标。每完成一项保存可恢复记录；只有队列及约定交付完成才结束目标。
- 实机证据不足时保留待验收项，继续其他独立调查；用户要求暂停时保存断点并停止派发。
- 用户已用任务完成券推进的角色按“绕过卡点”记录；completed、角色继续推进或暂时无人卡住都不能替代正常流程验证。
- 玩家样本不足时，以匹配客户端、真实PVF、协议及事务回归推进可行修复，给用户一份包含前置、步骤和预期结果的实测清单；不把等待真实过图录包设为所有修复的前提。
- 使用持续更新的在线反馈文档时，先处理已固定的队列，再按用户指令读取新快照，比较内容、定位和颜色，只追加新增或回归条目，保留历史状态与完成归属。

## 复用

在支持技能的环境调用 `$seeker`，或明确说“按 Seeker 工作流继续主线任务”。先读取本文件、方案索引和本机交接，再核对本次角色与授权。无需复制上一会话的完整上下文。

## Syncer 源码交付

GitGud 上游 master 是唯一权威源码。每项独立修复、验证、文档及客户端脚本分支均补齐或更新面向上游的 MR；出现冲突由 Syncer 保留双方有效逻辑、验证后非强推解决。按用户当次授权与评审状态合并，并读回上游 SHA。GitHub 只由 CI 单向快进镜像，不再双 fork 并行开发或创建 GitHub 同步合并提交。研究候选保持草稿和依赖说明；仅推 fork 不能作为贡献闭环。源码合并、客户端 Release、玩家通道、累计部署和实机验收分别记录，具体流程见 [仓库同步](REPOSITORY_SYNC.md)。
