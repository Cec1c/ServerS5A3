# 公会地下城个人奖励条

目标：公会地下城结算后右侧奖励条增加，满条在同一结算事务发放真实 PVF 配置的礼盒；重放不重复累计或发奖，重新入场恢复角色进度。

已核对客户端完整 SHA256 `686eaa069ba3cc374520d249628efc9de89bf0892ad45ad1e4bd2d2206b08dc5`。其 class0/NOTI742 接收一个 u32，存入公会地下城 manager+0x40。绘制函数按每百分比 1.2 像素裁切 120 像素奖励条；入场客户端会清零该字段。它独立于 NOTI741 的全公会净化计数，不能用净化或冒险团胶囊替代。现有服务端在修复前没有维护此个人奖励进度，也没有发送742。

真实 PVF 的 `[repeat clear bonus reward]` 指定礼盒和数量，但不包含每次增长倍率。本次确定的规则为每角色每次成功通关增加10%，累计10次发1盒；`dungeon_policy.repeat_reward_percent` 可设置1～100，省略或0采用默认10。该默认是明确的服务端规则。每个角色分别累计，不跟随月度公会净化重置，不凭历史净化补发；变更倍率保留已有百分比。只有表中有额外奖励且通过既有公会副本准入/结算的通关才累计。

实现范围：guild目录解析及冻结规则、dungeon结算事务、bridge入场和结算投影。个人余额放原角色stats，奖励与EXP、物品、净化及永久结算回执一次提交。达到100%发真实配置数量并保留余数；本次结算显示100%，下一次入场显示余额。旧结算回执重放保留原结果，不补发。

验证：原版累计失败与修复后十次通关/再次循环；并发重放、满包及晚期事务失败、角色隔离、换月与规则变更、真实PVF目录；742原生接收与绘制宽度。部署后实测通关增长、满条礼盒、重新入场与重登。源码候选不等于已部署或游戏验收。

协议依据：接收函数 VA `0x013A4C10`、绘制函数 VA `0x013A3100`，映像基址 `0x00400000`；选图路径 `0x036D312D` 经 `0x018C10A0` 清零进度。定点原生执行校验包体恰好消费4字节及0～100%的裁切宽度，不执行图形系统。入场投影接在队长／队员共用的 START_MAP 尾段，结算投影使用已提交回执冻结的正文。
