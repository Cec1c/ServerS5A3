# 公会聊天独立投递

公会聊天原来在发送前预约全部在线同会角色的资产锁，并持锁逐个写回包。一个成员正在处理资产事务，就能使其他人的整条聊天在等待3秒后被拒；一个停止读取数据的连接还可能让广播长期持有所有参与者的锁。

## 修复行为

- 发送者只预约自己的角色，核对会籍、账号和会话代际，沿原事务领取聊天贡献，并发送原有op17确认和NOTI65回显。
- 释放发送者预约后，将独立消息副本非阻塞提交到各接收者已有的会话队列。不新建逐消息线程，不等待其他会话的队列腾出空间。
- 每个接收者只预约自己；从入队开始最多3秒。队列已满、消息过期或成员繁忙仅影响该接收者，记录阶段及错误，不取消其他成员的消息。
- 在取得写锁后重新读取会籍、入会时间和角色账号，验证原会话代际；排队期间退会、换会、重新入会或换角的旧消息不投递。
- 聊天确认、通知和可选贡献投影使用限时写入，继续复用原序号分配、正文编码和DPROTO。失败写入关闭对应连接，避免在已经部分写入或编码推进后的流上继续发送；仅等待写锁超时且未写入时不关闭连接。在释放写锁前清除本次deadline。

角色资产事务本身保留原锁。聊天不会再将接收者的事务锁与其他成员串起来。掉线/过载期间丢弃的消息没有离线补发功能；可选贡献投影失败后仍从已提交的背包或邮件状态恢复，不重复扣费或发币。

## 验证与适用范围

原失败回归：仅另一名在线同会成员持有资产预约，旧实现返回op17正文`0001`；修复后发送者及健康成员立即收到，短时繁忙成员在释放预约后独立收到。

回归覆盖真实会话队列、队列满、并发发送、不读取数据的连接、写失败、换会/退会/重新入会/替换会话、排队正文不可变、写锁等待后重新校验、DPROTO和deadline恢复。贡献币背包行、满栏邮件、贡献点通知与原投影逐字节对照，并保留原每日幂等测试。

这是服务端投递修复，op17/NOTI65布局不变，不需要PVF或EXE修改。自动测试证明上述阻塞条件与恢复行为；玩家反馈中的输入框本身无法输入文字，仍须与“回车发送后没有消息”分别验收。

## 玩家验收

1. 同会两人分别在同频道和不同频道发送文字，发送者回显、同会成员收到，外会成员看不到。
2. 一人打开公会仓库、领取红包或操作守护神期间，另一人连续间隔发送；健康连接的聊天持续正常。
3. 一人掉线或网络中断时，其余同会成员继续聊天；原成员重登后新消息正常。
4. 组队前、组队中及退队后分别测试公会聊天；退会角色不再接收后续公会消息。
