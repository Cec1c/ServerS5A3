# 公会守护神与公会战：协议结论和接收候选

当前候选已接通守护精气的登录、推荐图、公会图收入、每角色每日额度和1297/1284投影。首次召唤费用待运营选择，召唤与公会战战斗流程尚未实现。收入默认关闭，兼容客户端发布后再启用。下文先保留协议研究，最新实现与验收入口见末节。

## 基线与已确认原因

- 源码基于公会地下城候选 `2265aa9f280011d4b8cc6c0976f518834c1da897`，保留该单改动。
- 客户端：V166，SHA256 `0e16090f0e4e3ac830f70183c814f5b24724cec235935e6c1221bf2d865d4243`，111902720 字节。下文地址均为该模块 VA；复用时先核对完整摘要。
- PVF：SHA256 `94a2549598816198115340f84c0be2d31603ddeea58f70f27afe6f73b25e3df7`，只读复用提取结果。
- 配套 dstr：SHA256 `ee8904c8540ef63807dc984604a3ea0f5cc4040228e5ac2e95d490c03d21ec08`。

本轮接线前，服务端只有 `CmdPacketAgitWarGuardian=1350` 枚举，没有召唤 handler 或公会战状态 owner；现有公会里程、个人贡献也没有两种精气的收支模型。客户端接收门控拒绝 class0/1297 与 class1/1350。这两个缺口分别需要服务端实现和客户端接收支持。

## 已验证的原生契约

### NPC 请求与管理窗口

NPC1500/1501 的 `[attend guardian]` 参数分别为 1、2。字符串注册 token 为 `0x13D6`；实际 token switch 经 `03A9731C` 返回 role `0xD4`（212），与发送入口 `0354D991` 调用 `029227F0(212)` 一致。相邻初始化分支中的 `0xDB` 属于别的 case，不能据此判定编号错位。

`03AA264B` 后的解析尾段将 role 参数写入配置对象 `+0x174` 的 map；完整原生 getter 从运行 NPC 的 `+0x1A4` map 取值。有限验证运行了原生 token switch、已有 map 节点写入、完整受保护 getter 和发送片段；配置对象到运行 NPC 的构造复制仍由夹具显式提供。

发送正文是四个小端 u32：`[8, guardianID, 0, 0]`，共 16 字节。管理窗口 `00EE4D00` 构造确认 vector `[8, selectedGuardianID]`，经 `00EDFD40` 发出同一正文。`00EE9A1A` 另发 action7；本单没有将其等同于购买或召唤。

1350 应答回调 `01067EF0` 的成功分支直接返回，不产生拥有或出战状态。错误 22/223 对应“精气不足”，96 对应“当前频道非公会频道”，100 对应“您还未加入公会”。这些是客户端提示映射，权限判断仍需服务端实现。

### NOTI1297 状态

`01077450` 使用 `037E8430` 读取固定 `0x895`（2197）字节，再复制到当前公会 data 对象 `+0x2E05`。下面的偏移均相对报文正文：

| 偏移 | 已确认用途 |
| --- | --- |
| `+0x17`、`+0x1B` | 守护的精气 AP、斗争的精气 GP，已由原生绘制位置和提示命中对应 |
| `+0x44` u32 | 当前出战守护神 ID |
| `+0x50` | 40 条、每条 49 字节的建设记录，字段未完全解开 |
| `+0x7F8` | 5 条、每条 18 字节的守护神记录 |
| 守护神 row `+0` u32 | 守护神 ID |
| row `+4` i8 | 等级；1…50 分成 5 星、每星 10 级 |
| row `+5…9` | 五项技能等级 |
| row `+10`、`+14` u32 | AP、GP 投入进度原值；对应 action0/action1 请求的第三个 u32 |

原生 `03C1B2D0` 默认构造不是全零：正文 byte1=`FF`，`+0x876`、`+0x878` 两个 u16 均为 1，其余为 0。构造默认值只能说明空状态布局，不能代替服务端真实建设、赛季及资产数据。

`01069040` 查找守护神记录；`010690E0`、`01069130` 分别取星级与星内等级。`01066190(true)` 读取出战 ID；`01066250` 判断出战 ID 非零。因此“拥有记录”和“选择出战”是两个状态。重复接收采用整份覆盖；新公会空快照会清除旧记录与旧出战 ID。

状态复制后，非零出战 ID 会触发 `010763D0` NPC 更新；场景内还有 `01068D10`/`0106A630` 分支。本单替换了这些 UI/NPC 副作用，没有执行完整城镇刷新。

### 两种精气与战斗入口

匹配 dstr 的 49487 明确显示“需要使用%d守护的精气和\n%d斗争的精气。\n是否进行召唤？”。PVF 两个守护神的 `[ap]=50000`、`[gp]=1000` 经 `03B747B4`、`03B747D0` 写入配置 `+0x40/+0x44`，确认窗口 `00EE4DC0/00EE4DC6` 读取这两个值。它们不能换成 `Guild.Mileage` 或 `Member.ContributionPoints` 扣除。

`00F01270` 先调用 `01066250`，无出战 ID 显示 100000875“召唤守护神后，可以参加公会战。”；后半段静态路径准备 town8/area2、坐标437/321，再进入场景切换。`03705DD4` 也检查该条件。本单原生执行覆盖拒绝分支与条件 getter，后半段只做静态核对。

## 精气与首次召唤续接

新增28项原生/窗口核对通过。`0106CD24`原生绘制body+1B在右、+17在左；以各自实际文字位置运行`0106CE7B`的鼠标命中判断，分别得到100000873“斗争的精气”和100000872“守护的精气”，两个显示之间不弹提示。配置AP/GP与确认文案顺序相符。

`00EE4AE8`通过真实row getter构造两种投入窗口vector：`[0,id,row+10,level]`、`[1,id,row+14,level]`。`00EDFBA0`实际发送`[action,id,进度原值,输入量]`，最后一项取窗口+290，并拒绝非正输入。第三项是客户端看到的旧状态，后续服务实现需要和权威状态比较；这不能自行证明幂等或退款规则。

实际token switch确认AP token8A9进`03B7500F`，写config+510；GP token8B7进`03B7507C`，写config+524。原生循环将真实数组依次解析为AP `{0:10,1:15,2:15,3:30,4:0}`、GP `{0:30,1:15,2:40,3:15}`。这里只确认下标与数值；初始化注册之后的相邻跳转不是当前token分支。dstr100001004/100001005提供“成员签到、推荐地下城、公会地下城”与“参加公会战”的类别说明，未给出完整数组下标映射。

首次NPC显示并不是首次领取资格：`01077C1E`检查当前公会的出战ID；ID为0时，在配置地区进入`01068D10(scene,true)`。已有守护神记录但未选出战、没有当前公会对象也会走同一显示分支；选出战后才进入隐藏分支。这组反例说明不能把“看见首次NPC”或“当前出战ID为0”当作服务端免费发放依据。NPC action8与管理收费action8正文一致，也没有首次标志。

上述原生窗口与累计`df9c33ed…`逐字节一致。夹具替换坐标缩放、UI绘制、整数流、容器插入、guild对象查找和网络writer；生产状态、精气事件生产者与召唤事务仍未实现。

### 收入提示不是收入事件或余额更新

`01077B73`将`010688C0`注册为NOTI1284（`0x504`）。完整receiver通过原生`037E83C0`顺序读取两个32位整数，第一项大于0显示100001011“已获得%d守护的精气。”，第二项大于0显示100001012“已获得%d斗争的精气。”；零和负值均不显示。正文恰好8字节，没有事件编号或奖励数组下标，函数本体也没有更新1297状态的写入。

新增23项原生检查通过：运行真实注册参数生产、完整receiver及reader，覆盖单种/两种正数、零、负值、读长、栈与callee-saved ABI，并监测公会快照写入。格式化、文本查找、UI消息队列和注册存储作适配，输入金额及快照为人工夹具。三个相关代码窗口在累计输入一致。发行与累计输入的class0/1284门控均为拒绝，守护神候选保持该决定；以后接收入提示时需另行验证并补这一精确通知，1297仍负责余额快照。

## 收入接线前的研究断点（历史）

先闭合精气与首次召唤契约，作为单独可验收单元：

1. 余额方向、row投入进度及action0/1请求字段已闭合；继续确定投入与等级变化、进度保留/重置的服务端规则。
2. 将 PVF AP 奖励五项、GP 奖励四项与真实事件一一对应，确认首次 NPC action8 是否有特殊费用，以及资金、建设和赛季的归属。仅有数组值不能确定事件索引。管理窗口 action8 已有收费文案，但不足以证明首次 NPC 分支采用同一政策。
3. 明确后新增公会战领域状态与原子收支 owner，复用现有公会事务和持久幂等回执；bridge 校验当前成员、同会、角色/会话代、NPC/场景及权限，提交后广播 1297。重复请求返回已提交结果，换会/过期会话拒绝，重进从权威状态投影。
4. 用生产事务生成的报文交原生接收器消费，补齐同会刷新、重复不多扣、回滚、重连及下一战斗动作的 RED/GREEN，再集成对应客户端门控。不得把 `1345/body=2` 现有首次进城 ready 分支覆盖成通用状态请求。

尚缺的是上述生产规则，不是玩家录包本身。两轮已尝试匹配PVF/dstr、源码/历史搜索、静态交叉引用和有限原生执行；首次大客户端REA伪代码导入超时，后续未重复导入。PVF内四个官方指南地址当前返回404，补充检索也未得到可核验的首次费用条款。没有据此选择免费发放或强扣50000/1000。完整召唤、同会刷新和持久收支仍待这些规则明确后实施；公会战匹配继续保持独立范围。

最小未决输入已收敛为三类：奖励事件到AP/GP数组下标及每日额度主体；首次与再次action8的收费/拥有/出战状态转移；精气及守护神状态的初始化、赛季边界与保留策略。对应客户端入口分别为`03B7500F/03B7507C`、`0354D991/00EDFD40/01077C1E`与`01077450/03C1B2D0`；这些路径消费配置或服务端状态，没有给出权威生产政策。后续应取得相应服务端规则或明确的运营规则，再进入原子事务实现；复跑显示条件或成功ACK不能补足这些输入。

### 状态与事务

`guild/essence.go`从实际PVF读上限和四个已知奖励。公会JSON新增独立 `essence.ap/gp`，角色stats保存 `guild_essence_day_end/day_ap/day_login`，换会、解散、退会后重入均不能重置角色日额度。日边界沿用既有北京时间06:00服务日，不依赖宿主时区；现有历史精气正文只写每日，这一时刻是明确采用的服务端运营规则。

登录通过 `GuildUnitOfWork` 同时保存角色日记录和公会余额，提交前后检查当前会话；结算使用 `GuildSettlementUnitOfWork` 与EXP/SP、物品、贡献及永久完成回执一次提交。超过额度只发剩余额度；满额、零奖励、重复登录不发1284；旧永久结算回执和可识别的旧角色回执不补发精气。余额溢出、损坏日记录、时钟倒退、过期会话失败回滚。已有角色资产预留保证绑定在提交期间不被换角替换。

公会图组队身份在准入时冻结；不要求好友关系。当前最小单元没有将临时掉线、复活状态另立奖励资格，后续如需“结算时仍在队”规则应补该独立依据和共享完成点，不能让每名成员结算时随意重算出不同组别。

1297 body固定2197字节，余额为+17/+1B；收入候选最初其余使用原生构造默认值。[已有状态单元](GUILD_GUARDIAN_PURCHASE_CONTRACT.md)改为同时投影持久拥有/出战，避免收入刷新清空已有状态；赛季等尚未实现部分仍保留构造默认值。1284仅实际新增量，两LE32字段AP/GP；本单GP永远0。同会成员通过其事件队列收到权威1297，重校角色代和当前公会，满队列时下次公会投影/重登恢复；收入提交不依赖通知投递成功。重复结算只补快照，不重复提示。
