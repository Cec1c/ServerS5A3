# 公会守护神与公会战：协议结论和接收候选

本单已完成守护神请求、状态接收和出战条件的有限原生验证，并提供两个报文的接收门控候选。服务端召唤事务尚未实现，公会战尚未恢复。下一步需要闭合两种精气的权威收支与初次召唤规则，再接入持久状态；候选不单独发行。

## 基线与已确认原因

- 源码基于公会地下城候选 `2265aa9f280011d4b8cc6c0976f518834c1da897`，保留该单改动。
- 客户端：V166，SHA256 `0e16090f0e4e3ac830f70183c814f5b24724cec235935e6c1221bf2d865d4243`，111902720 字节。下文地址均为该模块 VA；复用时先核对完整摘要。
- PVF：SHA256 `94a2549598816198115340f84c0be2d31603ddeea58f70f27afe6f73b25e3df7`，只读复用提取结果。
- 配套 dstr：SHA256 `ee8904c8540ef63807dc984604a3ea0f5cc4040228e5ac2e95d490c03d21ec08`。

当前服务端只有 `CmdPacketAgitWarGuardian=1350` 枚举，没有召唤 handler 或公会战状态 owner；现有公会里程、个人贡献也没有两种精气的收支模型。客户端接收门控拒绝 class0/1297 与 class1/1350。这两个缺口分别需要服务端实现和客户端接收支持。

## 已验证的原生契约

### NPC 请求与管理窗口

NPC1500/1501 的 `[attend guardian]` 参数分别为 1、2。字符串注册 token 为 `0x13D6`；实际 token switch 经 `03A9731C` 返回 role `0xD4`（212），与发送入口 `0354D991` 调用 `029227F0(212)` 一致。相邻初始化分支中的 `0xDB` 属于别的 case，不能据此判定编号错位。

`03AA264B` 后的解析尾段将 role 参数写入配置对象 `+0x174` 的 map；完整原生 getter 从运行 NPC 的 `+0x1A4` map 取值。有限验证运行了原生 token switch、已有 map 节点写入、完整受保护 getter 和发送片段；配置对象到运行 NPC 的构造复制仍由夹具显式提供。

发送正文是四个小端 u32：`[8, guardianID, 0, 0]`，共 16 字节。管理窗口 `00EE4D00` 构造确认 vector `[8, selectedGuardianID]`，经 `00EDFD40` 发出同一正文。`00EE9A1A` 另发 action7；本单没有将其等同于购买或召唤。

1350 应答回调 `01067EF0` 的成功分支直接返回，不产生拥有或出战状态。错误 22/223 对应“精气不足”，96 对应“当前频道非公会频道”，100 对应“您还未加入公会”。这些是客户端提示映射，权限判断仍需服务端实现。

### NOTI1297 状态

`01077450` 使用 `037E8430` 读取固定 `0x895`（2197）字节，再复制到当前公会 data 对象 `+0x2E05`。下面的偏移均相对报文正文：

| 偏移 | 已确认用途 |
| --- | --- |
| `+0x17`、`+0x1B` | 两种精气的显示值候选；AP/GP 对应方向待核 |
| `+0x44` u32 | 当前出战守护神 ID |
| `+0x50` | 40 条、每条 49 字节的建设记录，字段未完全解开 |
| `+0x7F8` | 5 条、每条 18 字节的守护神记录 |
| 守护神 row `+0` u32 | 守护神 ID |
| row `+4` i8 | 等级；1…50 分成 5 星、每星 10 级 |
| row `+5…9` | 五项技能等级 |
| row `+10`、`+14` u32 | 两个字段，权威语义尚未闭合 |

原生 `03C1B2D0` 默认构造不是全零：正文 byte1=`FF`，`+0x876`、`+0x878` 两个 u16 均为 1，其余为 0。构造默认值只能说明空状态布局，不能代替服务端真实建设、赛季及资产数据。

`01069040` 查找守护神记录；`010690E0`、`01069130` 分别取星级与星内等级。`01066190(true)` 读取出战 ID；`01066250` 判断出战 ID 非零。因此“拥有记录”和“选择出战”是两个状态。重复接收采用整份覆盖；新公会空快照会清除旧记录与旧出战 ID。

状态复制后，非零出战 ID 会触发 `010763D0` NPC 更新；场景内还有 `01068D10`/`0106A630` 分支。本单替换了这些 UI/NPC 副作用，没有执行完整城镇刷新。

### 两种精气与战斗入口

匹配 dstr 的 49487 明确显示“需要使用%d守护的精气和\n%d斗争的精气。\n是否进行召唤？”。PVF 两个守护神的 `[ap]=50000`、`[gp]=1000` 经 `03B747B4`、`03B747D0` 写入配置 `+0x40/+0x44`，确认窗口 `00EE4DC0/00EE4DC6` 读取这两个值。它们不能换成 `Guild.Mileage` 或 `Member.ContributionPoints` 扣除。

`00F01270` 先调用 `01066250`，无出战 ID 显示 100000875“召唤守护神后，可以参加公会战。”；后半段静态路径准备 town8/area2、坐标437/321，再进入场景切换。`03705DD4` 也检查该条件。本单原生执行覆盖拒绝分支与条件 getter，后半段只做静态核对。

## 本次客户端候选

`scripts/client/patch_guild_guardian_v166.py` 只接受上述完整 V166 输入，将 `02523A13` 的门控调用接到已有 `.r195rx` 节内 `06EAD200`，只新增 class0/1297、class1/1350。其他报文返回原 `06EAD100` 链；疲劳541及既有接收修复保持。

输出长度及各节地址保持，差异限定为调用、helper 字节、节虚拟长度和 PE checksum 四处。脚本要求独立的新输出文件并读回验哈；不改接收器、不生成服务端成功回包。其他公会战通知的门控仍需逐项匹配消费入口，不能从这两个报文推广到全玩法。

离线验证命令：

```text
python scripts/client/patch_guild_guardian_v166.py --input <exact-V166.exe> --output <new-candidate.exe>
DNF_GUARDIAN_V166_CLIENT=<exact-V166.exe>
python -m unittest discover -s scripts/client -p test_patch_guild_guardian_v166.py -v
```

环境变量按所用 shell 设置。测试复用现有原生 harness，需要 Unicorn/PE 工具依赖；没有匹配 EXE 时会跳过，不能计为已验证。

实际结果：4 项自动测试、0 跳过。class0/1 各遍历全部 65536 opcode，前后只有上述两项由拒绝变接受；检查其他 class 代表值、栈及 callee-saved ABI、四处差异、checksum、Windows `SEC_IMAGE_NO_EXECUTE` 映射、错输入和覆盖拒绝。没有执行目标 EXE 进程。

另有 24 项状态/ACK/确认发送原生测试、12 项 NPC role/发送验证。状态均为显式人工夹具；网络 writer、guild data 查找及 UI 副作用有替换。它们证明布局与条件，不是生产 Go 回包、资产事务或游戏内验收。
