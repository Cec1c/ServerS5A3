# START_MAP 成员作用范围

固定客户端 SHA256：`534b5ef166d0090d1ab88e01f5f443721abf97eabfacfb007e04e30fd9d51b24`，以及正式 V203 `b63d35bb28ba70353af5388cdaea4f2f8294cacc5064fcbb31db175519a02783`。两个输入均执行32组，工具记录实际输入摘要。

`0x01FF9993..0x01FF9A64` 消费 START_MAP 最后的成员选择字节。0..7 查找对应槽位的模型并更新该模型的房间关联；`0xff` 遍历全部八个槽位，对存在的模型执行同一更新。选中槽位的模型缺失也会落到全员遍历。这个字段表达本次转移的作用对象，不是收件人的身份。

服务端整队进图和同步过图原先对每个收件人填写其自身槽位，因而只更新该客户端的自身模型。现在这三处完整/缓存报文使用 `0xff`，保持角色对象键、队伍槽位、共享种子和地图对象规划不变。底层 typed packet 仍允许表达指定槽位；未把所有协议中的槽位字段替换为 `0xff`。

`scripts/client/test_start_map_member_scope.py --exe <匹配文件> --output <私有报告>` 执行上述原生窗口及原始模型访问器/关联设置函数。字节读取和坐标到房间查找是明确列出的夹具；报告记录32组结果。参数、输入摘要不符则拒绝，不启动游戏。

Go 回归覆盖二、三、四人真实入口、每人只收一份START_MAP、种子/地图/怪物键一致，以及各身份槽位的完整过图、刷新和缓存回访。旧实现的全员作用范围断言失败，改正后应通过。这些结果确认协议字段错误，不单独证明所有重复怪物、技能或模型现象均已在游戏画面消失；后续实机按首局、重进、换房和重新组队分别验收。
