# 结算事务的角色归属预读与并发更新

## 成因与目标

角色结算先在事务内普通读取角色归属，再锁账号、再锁角色。普通读取建立了一致性快照；等待账号锁期间，其他事务可能更新角色行。MariaDB 随后的锁定读取可返回错误 1020（Record has changed since last read），使结算回调未执行。已完成副本的后续结算因此可能中断。

目标是消除这一过早快照，保持账号先于角色的锁顺序、角色归属复核和同一物理事务内的奖励写入。

## 最小修改

在开启事务前，从写入主库只读获取账号提示。开启事务后按既有顺序锁账号与角色，并再次验证角色仍属于该账号。提示不授予操作权限；角色已删除或归属变化时拒绝执行回调。公会结算已有明确 owner，继续先锁公会登记、再锁账号、再锁角色。

范围为 MySQL 角色结算单元、锁顺序夹具与独立真实数据库回归。不更改业务发奖、退出门禁、事务隔离等级或生产数据库配置，不吞掉数据库错误。

## 验证与验收

真实 MariaDB 回归在一次性回环数据库运行：事务 A 持有账号锁，事务 B 进入结算；通过 INNODB_LOCK_WAITS 确认 B 正在等待 A，再由 A 更新角色行并提交。修复前稳定出现 1020；修复后回调读到最新角色并正常保存。

另测等待期间角色归属变化，要求回调不执行、更新拒绝；旧锁顺序测试继续检查账号/角色与公会登记顺序。调用方式：

```text
go test -buildvcs=false -tags=mysql_integration -count=1 -run TestMySQLSettlementOwnerLookupSurvivesConcurrentCharacterUpdate ./internal/modules/dnf/repository/mysql
```

须设置 DNF_FATE_DISPOSABLE_DB=1，并只提供回环、未预选数据库的隔离 DNFBRIDGE_PLAYER_TEST_DSN。测试自己创建并删除专属库。

实际副本结算还需验证各队员收到结算入口、重复请求不重复发奖/统计、回城与重新登录完成。数据库红绿测试确认的是这条并发缺陷；不同现场错误需按各自证据关联。
