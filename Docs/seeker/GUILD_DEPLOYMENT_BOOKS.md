# 公会布置书恢复方案

目标：公会商人出售的布置书能够放置，消耗一本，向同会成员显示，并在重登后恢复。

当前链路缺少 837 建造请求的处理。匹配客户端发送 53 字节固定结构和 N 个 uint32 占地值；前 13 字节为未初始化前缀。服务端应忽略前缀，不把它作为身份或幂等键。后续字段依次为道具、背包槽、坐标、格子类型、宽高、格子数量、区域、客户端附带值。真实资源中的 132 本在售布置书均使用 `[deploy in isometric cell map]`，对象来自 passiveobject 索引。

客户端还有两个接收入口：777 为 39 字节建筑变更通知，191 为公会基地完整快照。建筑记录长 23 字节，与 1297 的固定设施表不同。当前匹配客户端的 837 ACK 和 777 通知被接收门控拦截，需要在最新正式客户端上叠加接收补丁。

## 实现

- 从实际 STK、OBJ 和 MAP 解析道具授权、占地形状及可布置格子。按地图矩形生成等距格子，每格四角都必须处于矩形并集内；复用原生坐标计算结果校验。
- 在公会与背包事务内检查成员、真实库存、道具期限、当前场景和占地冲突，扣一本书，保存建筑及永久请求回执。重复请求恢复当前投影。
- 提交后刷新库存、发送 ACK 和同会建筑通知；初始公会状态发送完整快照恢复建筑。广播前复核当前成员及会话代际。
- 客户端补丁以完整摘要锁定最新正式 EXE，限定接收修改范围；保留后续已发布修复。

## 验证目标

- 原生完整点击发送函数输出与服务端解码一致；格子生成和位置计算与原生一致。
- 不同尺寸、镂空占地、边界、重叠、满区域、失效书、换角、跨公会、重放及并发都符合事务结果。
- 通知和重登快照进入真实客户端记录与场景创建链；成功 ACK 不携带额外业务正文。
- 隔离数据库验证扣书与建筑同事务，保存失败不扣书，重试不重复创建。
- 上线顺序为兼容 EXE 正式发布及玩家通道读回，再由 Syncer 发布服务端。

## 协议与资源依据

- 正式 V177 输入 SHA256：`027eca60196f8e22b7d05a9cad4ae37fe0098ab48e3048714b8ceb9270f5e752`。补丁严格匹配该输入；新正式发行需重新核对和叠加。
- 23 字节建筑行：u32 建筑键、u32 passiveobject、u32 成员角色编号、u8 区域、2 保留字节、i16 X/Y、u32 完工时间。角色编号与原生公会成员名单首个 u32 写入的字段一致。
- 完整快照首字节 1，8 区各 64 行；登录先发 1297 初始化原固定设施，再发 191 恢复布置。后续增量先发 777、再发 1297，同一建筑按键更新，维护费变化不会再次重建基地。
- 工期从 ETC `building construct time` 读取，匹配资源为 180 秒。布置书 action 的第三个整数保持未使用，不将其命名为等级。
- 原生建造前检查单本维护值不超过 300。区域使用 64 行容量和真实占地约束，不额外引入未证实的区域累计 300 上限。

## 回归与发布

服务端回归覆盖 132 本真实提取资源、原生格子集合摘要、扣书与建筑同事务、并发重叠/重放、过期书、失败回滚、同会刷新和换会清理。原生测试覆盖完整发送函数、191/777 接收及场景创建控制流、实际 Go 回包、全 opcode 门控差异和 Windows 映像映射。场景资源、对象工厂、占地绑定、STL 和 UI 是原生夹具的适配边界；游戏内画面、建造完成及双人同步由实测验收。

`patch_guild_placement_v177.py` 只放行 class0/777 与 class1/837，并归零 837 请求前 13 字节。保留 V177 已有接收链及其他修复。服务端仅在既有公会精气功能启用时接受布置。

持久状态新增 `placements` 和永久 `placement_receipts`。发布先准备保留这两字段的兼容构建，再启用交易；回退也必须保留这两字段，避免旧版本重写公会注册表丢失建筑或回执。客户端正式资源和实际玩家通道完成读回后，方可启用依赖它的服务端。

上线验收：两位商人的不同尺寸布置书可落地、扣一本、等待建造完成；同会另一角色即时可见；重登保留；重叠失败不扣书。移动/拆除和练习战斗由对应后续条目接续。
