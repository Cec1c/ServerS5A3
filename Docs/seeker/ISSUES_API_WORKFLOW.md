# Seeker：论坛 BUG 持续修复流水线

使用论坛 API 持续读取、筛选、认领和处理 BUG；修复通过上游 MR 合并后，将分支、MR、合并提交及验证结果回写到原反馈。论坛问题ID是主键，关联已有BUG编号、方案、修复和验收记录。当前账号及授权范围由本机流水线配置提供。

## 目标与批次

每轮先收回当前批次的修复、合并和验证结果，再读取新反馈。按影响和可复现程度选一批独立问题，批次名为当地日期 `YYYY-MM-DD-修复流水线`；同日追加批次使用私有批次序号区分，论坛仍显示日期名称。优先处理阻断功能及主线任务；任务类别以外的功能BUG也进入分流。

每批保存问题ID、原状态/优先级、分流依据、负责人、最新编辑版本、复现步骤、代码基线、允许修改文件、测试、源分支、MR、合并SHA、部署及验收状态、最后一次回写和下一步。完成当前批次后继续下一批；没有可执行项时保存等待原因，后续运行从该记录续接。新的流水线目标取代旧队列驱动，旧资料作为查重和复现依据保留。

## 分流顺序

1. **查重。** 对照论坛详情、附件、事件、已关闭反馈、旧台账和已有MR。依据同一功能、触发条件、版本和失败行为关联，标题相似只列为候选。确认重复后设置 `duplicateOf` 和 `duplicate`，回复主问题编号；原反馈及独有证据保留。旧问题修复后的新失败先核对部署版本，按回归处理。
2. **判断合理性与类别。** 比较当前功能约定、PVF定义和实际行为。合理但属于新增功能/平衡调整的请求单列候选，说明分类；与既定设计一致、操作问题或账号服务诉求说明原因后退出BUG流水线。暂时缺信息使用 `needs_info`，不以“未复现”直接关闭。
3. **判断能否复现。** 查已有日志和附件，确定具体功能/任务/物品、前置、操作、期望/实际、客户端及服务端/资产版本。能从代码和既有证据还原的资料自行补齐；关键缺项只回复最小补充清单。记录“具备复现输入”和“已复现”两个阶段。
4. **校正优先级。** 按实际影响、范围、发生率及临时处理办法重评，记录原值、新值和一句依据。玩家自选等级是参考值。
5. **选批认领。** 从可执行项选择本轮批次，经 `/issue-assignees` 核对本机当前账号ID；保留已有其他负责人的工作。选中项分派当前账号并置 `accepted`，回复入列说明。实际开始复现/修复时置 `fixing`。

| 优先级 | 依据 |
| --- | --- |
| P0 | 广泛持续不可用、严重数据破坏或正在发生且无法有效缓解的重大问题 |
| P1 | 崩溃、资产异常、主线/觉醒等核心流程被阻断，或高影响功能故障 |
| P2 | 局部功能错误，影响有限或有稳定替代步骤 |
| P3 | 轻微显示、提示或低影响问题 |

关闭可选活动后恢复登录的故障仍需修复，可按实际影响列P1；仅单次无掉落且缺随机样本时先补信息，不按描述直接断定掉落算法错误。

## 修复、合并与论坛闭环

1. Seeker解释成因并在 `Docs/seeker/` 留脱敏方案，明确文件、解决思路、测试与验收目标。在干净独立分支保留修复前/后SHA，复现原失败后实施精确改动。
2. 按仓库规则验证，保留失败与通过的对应证据。委派沿当前会话授权；DeepSeek执行明确的小目标并允许失败，复杂问题由Seeker/指定Helper处理。PVF写入交PVF-Writer。
3. 将分支推到贡献fork，通过上游MR集成；已有同项MR则续接。Syncer按本轮源码上传/合并授权处理冲突、检查评审及流水线，合并到权威主干并读回完整SHA。GitHub沿既有单向镜像流程同步。
4. 合并后在原BUG回复源分支、目标分支、MR编号/链接、合并SHA及一句验证结果。源码已合并待部署/实测时置 `verifying`，并写清下一项验收；该BUG验收条件已满足才置 `resolved`。复测失败回到 `fixing` 或 `needs_info` 并记录证据。
5. 精确回读负责人、优先级、状态及评论，更新批次台账后继续下一项。合并、发布、部署和实机验收分别记账；部署交Syncer沿既有授权与资源顺序执行。

简短回复模板：

```text
已列入 {YYYY-MM-DD}-修复流水线，由 {当前账号} 处理。优先级 {P级别}：{一句依据}。

与 #{主问题ID} 重复，合并跟踪；后续进展见主问题。

请补充 {最少缺失信息}，用于复现 {具体失败步骤}。

修复已合并：{源分支} → {目标分支}，MR !{编号}（{链接}），提交 {SHA}。
验证：{简短结果}。当前：{待部署/待游戏内复测/已验收}。
```

## 鉴权与读取

- 使用 HTTPS 和 `Authorization: Bearer <API_KEY>`。密钥从受保护的本机凭据文件或进程环境读取，公共文件只保留占位符。
- 每把密钥绑定一个游戏版本。DNF90 请求使用 `X-Game-Version: 90`；`gameVersion` 是游戏版本，`issue.version` 是并发编辑版本号。
- 先读接口定义，按 `GET /issues?offset=0` 读取各模块反馈，按需用 `module=quest` 或 `q` 过滤。每页30条，依据 `hasMore` 将offset加30，按问题ID去重；列表可能有截断，决策前读取详情。
- `GET /issues/{id}` 获取详情、附件与事件；原始反馈及日志保存在指定的 ignored 证据文件。`hasMoreEvents=true` 表示当前事件记录不完整，保留该事实。
- `GET /issue-assignees` 获取可分派负责人，精确匹配当前账号名并使用实际ID。私密附件通过同一受信API读取，认证头只发给配置的API源。

## 处理与回写

| 动作 | 接口 | 必要字段与依据 |
| --- | --- | --- |
| 新建问题 | `POST /issues` | `title/module/priority/actual`；先查重 |
| 精确修改内容 | `PATCH /issues/{id}` | 最新 `version` 和本次要改的字段 |
| 分派、状态和处理结论 | `PATCH /issues/{id}/triage` | 最新 `version`，按需提供 `status/assigneeId/priority/resolution/duplicateOf` |
| 补充处理说明 | `POST /issues/{id}/comments` | `body`，写原因、修改、测试、MR和实测步骤 |
| 回归确认 | `POST /issues/{id}/verification` | 最新 `version`、`resolved` 和实测结果 `body` |

状态按上述分流和闭环规则推进。已认领、已合并与玩家游戏内成功分别记账；完成券和技能锁定等临时办法作为处理步骤记录。

每次PATCH或verification前读取最新 `issue.version`；返回409时重新读取，保留他人更新后重建本次精确字段。写入后GET读回字段和事件。每条日期入列/合并回执在台账保存正文摘要，发前检查事件，避免重复；POST超时先查事件再决定是否重试。401/403核对密钥及版本权限；423等待问题区恢复可写；429按 `Retry-After` 延后。限流为每Key每分钟120读、60写，每IP每分钟600请求。

## 文件保存与脱敏

- 每次读写都明确列出输入、请求正文、输出和修改文件；输出使用独立的确切文件名。暂存或提交使用 `git add -- <明确路径列表>`，审查这些文件的diff和已暂存清单。
- 公共文档仅保留技术成因、算法、验证与操作说明；API地址使用配置引用或示例地址，密钥使用占位符。玩家身份、私密附件、原始报文、本机绝对路径、真实主机和网络配置留在ignored资料。
- API key不写入文档、请求正文、命令示例或日志。本机配置只记录凭据文件路径，凭据使用系统保护存储；子代理领取最小证据和文件范围，由Seeker完成API回写。
- 发布前检查所选文件中的凭据、身份和环境信息，保留脱敏检查结果与修改文件清单。本机入口及接口快照位置从 `local-notes/seeker/ISSUES_API_WORKFLOW.md` 读取。
