# 交易邀请与建立边界

当前客户端接受交易后，旧服务端先返回成功、再尝试建立交易；双方已离开同一区域时出现成功窗口但没有交易。重复建立还会清除参与者已有交易。本修复先建立受保护的握手状态，再通知双方；已有交易及提交中的交易保持原样。

## 协议依据

原生验证输入为 V186（SHA256 `0cfc74d29de563c6612b2118a47f5f731c80f3e5a16b17b9e0bfd70fbd93acc9`）及累计资料候选（`01b313275faf7b598211f4d8adb932e1b31ce4347827583a2df3cfa4d350e94c`）。两个完整摘要分别执行同一组验证。本项没有 EXE 修改，也不依赖资料候选新增功能。

| 方向 | 真实布局及消费行为 |
| --- | --- |
| 菜单交易 | 原生菜单经交易管理器发 op10，`u16 peer,u8 mode=1,u32 gold,u32 value` |
| 接受 | op11，`u16 peer,u8 mode=1,u32 gold`，共7字节 |
| 拒绝 | 相同前7字节，追加 `u16 reason=133`，共9字节；客户端关闭自己的邀请窗口 |
| op10/op11失败 | `u8 0,u8 error,u8 mode=1`；旧两字节包缺少 mode |
| class0/op8接受通知 | `u16 peer,u8 mode=1,u32 gold,u8 flag,u32 characterCreatedUnix`，共12字节；旧通用7字节包截断 |

创建时间来自角色仓储 `CreatedAt`。原生接收器用它显示“角色创建不足一周”的交易提示，并非随机字段。金币也读取权威角色记录；账号归属、角色ID和当前绑定必须匹配，时间/金币必须在原生有符号32位范围内。缺少创建时间时拒绝本次邀请。MySQL正常创建及插入路径已有非零创建时间补全，本修复不批量修改历史数据。

## 生命周期

- 邀请和接受均校验当前会话代次、同频道/区域及双方空闲，按角色顺序预留绑定。待处理交易邀请不能互相覆盖，也不能被普通邀请覆盖。
- 待处理邀请有服务端一分钟有效期，登记和消费时清理。该值是服务端策略，不代表原生UI计时器；拒绝消费邀请，迟到和重复接受不重新打开交易。
- 握手期间禁止加入报价与确认，两端通知完成后才开放交易。失败清理本次状态，以空 class0/op16 复位窗口；独立的有限恢复期限保证原握手超时后健康对端仍能收到复位。
- 网络锁和写入有期限。失败流关闭，预留释放；对端写失败不作为健康连接的错误向上传播。
- 沿用现有物品、金币、账号晶块、手续费与事务结算。双锁和双方最终确认后才转移资产，重复完成不再次结算。

## 验证与范围

基线 `c8a529ba3b78d05aa3575e77553067822e11bf90` 上已复现“不同区域仍成功”和“覆盖已有交易”；回归覆盖拒绝/迟到应答、过期/重叠邀请、错误元数据、现有/提交中交易、握手报价阻断、慢连接复位及预留释放。

完整交易回归从真实邀请开始，报价1000晶块和100000金币；单方最终同意时资产不变，双方同意后晶块5000→4000/1000，金币1000000→900000/1097000，重复完成不再转移。领域、bridge、control、list、vet、Windows/Linux构建和交易race检查通过。

`scripts/client/test_trade_invitation.py` 在两个输入上各通过5项检查：执行原生菜单/交易管理器、接受/拒绝发送器，消费Go实际导出的邀请、接受、锁定、完成和空回滚包。旧短失败包和短接受通知均验证越界，新包完整读尽；同时检查栈、保存寄存器、交易状态和消息。UI、对象/容器、资源、时间函数、保护标量和class0传输队列由明确适配器提供；原生标量读取及相关接收逻辑真实执行。

先设置 `DNF_TRADE_INVITATION_PACKETS`，用 `go test -buildvcs=false -count=1 ./internal/services/dnfbridge -run TestTradeInvitation` 导出回包；再设置 `DNF_TRADE_INVITATION_CLIENT` 并运行 `python -m unittest discover -s scripts/client -p test_trade_invitation.py -v`。缺少输入时明确跳过，不计通过。未配置一次性SQL测试库；真实双玩家窗口、物品交换与取消交互待上线后验收。
