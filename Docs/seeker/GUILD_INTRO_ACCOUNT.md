# 公会守护神入场动画按账号保存

目标：首次进入公会战守护神区域显示原生介绍，同账号再次进入、重登、换角色及重启服务后不重复；另一个账号保留首次介绍。

## 依据与方案
累计客户端的 PVF `[first enter video]` 由原生首次进入函数检查第二组通知标记42；播放窗口创建后原生发送 C2S503/u32(42)。服务端把503当作忽略的被动报告，既没有保存也没有恢复。原生 class0/440 的接收器接受 `u8 count + count*u8 id`，先清空第二组标记再逐项恢复；当前接收门未放行440。

在独立 accountnotice 领域中保存第二组0..127标记，使用已有账号元数据单键写入，幂等合并，不覆盖钱包、剧情或其他元数据。恢复完整已保存集合是原生440的覆盖契约要求。桥接层从已绑定、仍归属账号的角色接受四字节503；选角成功后、场景通知前恢复账号集合。未知类别/长度/编号/过期角色均不写入。没有观看记录的账号恢复空集合，不能在登录时替用户标记已看过。

客户端基于公会物品链接累计成品，仅开放class0/440，其他编号和类别回既有接收门。来源通知及其他累计补丁保留。不会修改PVF视频或原生播放函数。

## 验证与交付
覆盖旧客户端/服务端失败、新客户端原生完整dispatcher/440接收/标记检查/首次入场/503发送，重复进入与新进程恢复、不同账号、编号边界及原生ABI；Go生产报文双向重放、账号隔离/重建服务/重复/并发/错误存储/无效身份、选角包序及普通通知回归。按仓库完整Go、race、双平台及原生全编号门控检查后交Syncer串行发布。实际游戏内首次动画、重登和换角色验收独立记录。

## 原生证据定位

匹配输入为公会物品链接累计客户端，SHA256 `b053420ce498bff59c229ce8faef3974c9f9b6fc0c6f427c3b44d467d27e1010`。静态分析所用V183与该累计输入的以下九个函数块逐字节一致。

- `0x03705C80` 进入场景分支仅在 town=8、area=3 调用 `0x0106C4E0`。
- `0x0106C4E0` 检查第二组标记42，使用首入场视频构造742窗口，再标记并上报。
- `0x022894E0` 检查；`0x02289770` 标记并由原生标量写入器输出 `503 / 2A 00 00 00`。
- `0x02034320` 是已注册的 class0/440 接收器；`0x02289460` 清空第二组集合，`0x02289700` 恢复每个编号且不反向上报。

原生回放保留上述函数、完整dispatcher和真实计数/编号读取器；标准集合内存与视频UI端点使用适配器。另有六类别全65536编号验证，新增门控仅class0/440。无游戏进程执行。
