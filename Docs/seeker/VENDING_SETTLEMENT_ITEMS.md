# 黑钻售货机结算物品明细

目标：普通、高级售货机成功抽取后，原生结算窗口展示实际奖励，背包同步已提交数量。

匹配客户端：正式 V179，SHA256 `72254abd5214bc24f8bcb76a16184e07105dde33f4e762b4c71c2e264bc7789c`。

## 成因与方案

op215 成功回复已有币槽、剩余币、奖品 ID 与本次数量，但内嵌物品数恒为零。原生接收入口 `0x01FE64D0` 将内嵌物品转换到窗口向量；结算 `0x033044F0` 遍历该向量生成奖励显示。后续 op14 背包刷新不能补建这次结算列表。

领域事务返回奖励槽的提交快照。桥接回复追加 `count:u16=1`、`listType:u8=0`、标准 `raw[119]` 物品行；该行使用提交后总量，而回复头保留本次奖励量。继续发送 op14，处理币槽删除、契约自动激活和最终背包状态。

保持黑钻资格、物品期限、归属和容量校验。资格拒绝与成功后空结算分别验证。

## 范围与验证

- 领域 `vending/owner.go`、桥接 `vending_machine.go` 及对应测试。
- 用匹配原生接收与结算执行旧回复 RED、完整回复 GREEN；资源工厂、STL 和窗口输出使用适配器，接收解析与结算分支执行原始代码。
- 真实 PVF 的四台已注册机器和全奖池走完整请求分发，核对扣币、实际入库与回复明细。
- 覆盖连续两次抽取、已有堆叠、最后一枚币、资格缺失、背包满和过期；失败保持资产原值。
- 用户实测普通、高级机器：扣一枚币，显示一次奖励，背包与重登数量一致。

成功物品行属于服务端回包修复；失败提示与状态复位另需下面的客户端兼容修复。

## 累计客户端复核

V183 来源通知基线及后续累计客户端已带售货机拒绝复位分支，但 V186 的 ACK 分类器仍跳过 CMD215 错误字节。回调收到 `status=0,error=0`，无法进入已有的 `error=1` 复位分支。现场三次 `00 01` 失败回复均能重现：剩余一字节未消费、没有错误提示、pending=1、state=6、奖励对象为空。奖池本身有45个有效对象；state=6 且奖励对象为空使绘制跳过图标。

此前八项原生回归直接调用 `error=1` 回调，仅证明该分支有效。旧共用夹具把 `0x8BAB80` 替换为恒零，使另一些 dispatcher 测试也漏掉真实分类契约；这些结果不能证明完整失败收包链。共用夹具现保留真实分类器。

`scripts/client/patch_vending_ack_error.py` 只接受 V186 完整 SHA256 `0cfc74d29de563c6612b2118a47f5f731c80f3e5a16b17b9e0bfd70fbd93acc9`，只将 `0x8BAC75` 的 CMD215 分类字节由0改1，并重算 PE checksum。18/20/27保留特殊消费契约；成功分支、既有复位节、来源通知和其它累计内容逐字节保持。输出必须是独立新文件。

`test_vending_ack_error.py` 从真实 ACK dispatcher 执行分类器、字节读取器、回调、复位及结算：旧成品 RED、新候选 GREEN；连续三次失败与延迟 tick；失败后成功；新槽、合并与最后一币槽复用；111个真实 PVF 生产奖励回包；其它错误提示、其它 opcode 分类及修改范围。失败不能扣币、插入物品或生成奖励行。transport 解码、回调表查找、UI/计时、资源与容器是适配器，最终像素和游戏操作仍待实测。

通用复位工具见 `scripts/client/vending-reject-reset/README.md`，仅适用于缺少复位分支、指纹已确认的输入；不能单凭它证明完整收包链。V186不重复追加补丁节。后继正式发行沿来源通知基线累计修改，按 Release、实际玩家通道及依赖服务端顺序发布。
