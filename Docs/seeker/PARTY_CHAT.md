# 普通队伍聊天

目标：普通队伍消息按当前队伍名单发送，支持同队不同场景；退队、解散和重新组队后使用新名单。公会聊天保持独立。

匹配 V179 客户端 SHA256 `72254abd5214bc24f8bcb76a16184e07105dde33f4e762b4c71c2e264bc7789c`：聊天菜单第二项经 VA `02A0C16E` 选择类型 2；`02A03782` 发送 op17，正文为类型 u8、提示 u16、零 u32、消息 DSTR。原服务端将这类消息交给只接受类型 3 的普通区域聊天，因此返回失败。

实现使用 RuntimePartyManager 的当前成员关系，按绑定会话的完整代际读取队伍快照，并以数据库角色账号确认发送者；请求中的提示不决定身份和收件人。接收投递落锁后再次核对同一队伍、接收者会话代际和数据库账号归属。NOTI65 `0201B510` 支持类型 2 的具名消息，读取类型、结果、发送者 DSTR、频道、消息 DSTR、空辅助 DSTR，送入 `02A00710`。该路径不要求发送者处于接收者场景中，当前不跨连接频道投递。

依赖公会聊天投递隔离修复：复用限时写入，在接收者会话队列重新检查队伍和身份。仅变更聊天路由、独立处理器及测试，不写公会资产或玩家物品。

测试目标：修复前真实类型 2 请求被拒绝；修复后本人和同队收到，旁人不收到；覆盖队内不同场景、退队后旧缓存、重新组队、已换角和慢接收者。客户端定点执行菜单类型选择、真实 sender 和 NOTI65 reader，核对生产回包的名称、类型及文本。

实机验收：两人组队连续发消息，分别在城镇和地下城验证；退队后普通与公会频道可用，重新组队后只有新队伍收到。文本输入框可输入状态另行验证。
