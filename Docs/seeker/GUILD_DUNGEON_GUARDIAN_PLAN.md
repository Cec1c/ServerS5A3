# 公会专属地下城与守护神协议恢复方案

## 目标与基线

针对专属地下城全部锁定、守护神召唤无响应，沿实际客户端请求与 PVF 规则恢复对应领域状态和回包。本次已完成解锁规则与快照编码候选；生产入口、周期持久化、奖励事务和守护神闭环尚未接入。普通地下城公会积分、守护珠与勋章合成保持现有行为。

研究基底为 `dae368b`。匹配客户端为 V164，SHA256 `2d56c7086c3fd9bc029d932571504b7f89147e47f1d563684f74b9e467f4f8a2`；PVF SHA256 `94a2549598816198115340f84c0be2d31603ddeea58f70f27afe6f73b25e3df7`。客户端地址仅适用于这一完整摘要。

## 取证与实施顺序

1. 读取 PVF 的公会地下城目录、入口、开放前置、净化与周期规则；查客户端选图锁定和剩余时间的生产状态来源。先确定首图开放条件，再实现真实状态投影。
2. 沿通用入图和结算链，明确公会成员、地图、难度、周期以及运行实例归属。净化只由已确认成功的通关提交，重复结算不能重复累计，重新登录读取同一持久进度。
3. 追守护神 NPC 的召唤菜单发送端、服务端入口和客户端应答消费，确定消耗、权限、幂等与重登契约；再划定公会战所需的独立状态。
4. 领域规则放入 `internal/modules/dnf/guild`，持久修改沿既有 `Guild` 事务；bridge 只承担请求校验、协议投影和场景接线。资源规则使用现有 PVF 读取设施，资产修改另行处理。

## 验证与交付

每个确定的实施单元先建立失败回归，再验证修复后的领域与报文行为。覆盖首图、后续门槛、跨公会隔离、重放、重登与周期边界；召唤另覆盖消耗不足、权限和重复请求。测试使用隔离公会与数据库。

允许失败。未闭合的协议需保留具体函数、输入、已尝试方法及缺失证据，不用固定开放位或虚构进度代替状态。冻结后记录专项结果与尚需执行的完整检查，经独立分支和中文上游 MR 交付；本研究不部署。

## 专属地下城：已闭合的契约

V164 在 VA `043EC4D0` 注册 **class 0 NOTI741 → `013A4990`**。它与 class 1 CMD741 的公会创建许可互不替代。接收器先加载目录 0，再读取快照。缺失快照时目录指针为空，`013A0610` 对六图全部返回关闭；目录加载后，无前置的 8500 在通关次数为零时开放。

741 body 的字节布局如下，长度为 `17 + 8 * N`：

| 偏移 | 类型 | 已证明的用途 |
| --- | --- | --- |
| 0 | u8 | 转 bool，存 manager+0x30；不是首图开放位 |
| 1 | u32 | 存 +0x34；与上一个 bool 一起参与特殊 NPC 可用性/菜单，完整语义未定 |
| 5 | u32 | 存 +0x38；绝对结束时间戳，UI 减当前 Unix 时间后显示剩余时间 |
| 9 | u32 | 存 +0x3c；完整业务含义未定 |
| 13 | u32 | N，后续记录数 |
| 17+8i | u32 | 地下城 ID |
| 21+8i | u32 | 通关计数单位，非原始净化 gauge |

接收器用新 map 替换旧进度。NOTI742 → `013A4C10` 另读一个 u32 到 +0x40，当前不把它映射为净化总值或周期字段。

匹配 `etc/guild/guilddungeon/0_2way6dungeon.etc`：

| 地下城 | 每计数单位净化量 | 自身征服门槛 | 前置征服 |
| --- | ---: | ---: | --- |
| 8500 伤城 | 150 | 50% | 无 |
| 8504 | 75 | 50% | 8500 |
| 8507 | 50 | 50% | 8500 |
| 8505 | 50 | 50% | 8504 |
| 8503 | 75 | 50% | 8507 |
| 8508 | 30 | 100% | 8503 和 8505 |

六图 gauge limit 都是 10000。`03C73EE0` 对 `count * gain` 做 float32 比例计算、截断并夹到 0…100；`013A0610` 检查每个前置的**自身**门槛。因此 8500 的 33/34 单位为 49%/51%；8508 开放需要 8503≥67、8505≥100 单位，不能要求这两个前置各自达到 100%。8508 自身达到 100% 要 334 单位。

`worldmap/guilddungeon.wdm` 的 worldmap 37 用 `dungeon is not open` 条件画锁盖。选图 `035D6319`、入图 `0371E2DF`、锁盖 `03733A1A` 都调用相同开放判定。入图失败路径使用文本 ID 60457。8500 的 DGN 另要求最低等级 50、指定难度 2、入场疲劳 8；解锁计算不代替这些入场条件。

## 最小实现单元与接线位置

已实现的只读单元：

- `internal/modules/dnf/guild/dungeon_unlock.go`：从 PVF 提取文本解析不可变规则，计算净化比例和完整前置条件，拒绝重复 ID、缺失引用、依赖环和原生整数溢出。
- `internal/services/dnfbridge/guild_dungeon_snapshot.go`：按稳定 ID 顺序编码 741；保留未定头字段的 wire 名称，由后续权威 owner 提供值。没有注册 handler 或发送快照。
- 相应测试覆盖真实提取文本、33/34 与 66/67 等门槛、末图 AND、未知目录/ID、溢出及畸形规则。Go 输出报文已由匹配 V164 接收器和解锁函数消费验证。

后续接线应保持一个明确的事务边界：

1. 公会 owner 持久化周期标识、真实起止时间、每图计数。周期来源确认后再定义重置；现有 ETC 没给出可据以硬编码的月初或周重置时刻。
2. `handleDungeonSelectUpperPlannedForAdmission` 的 op16 链解析真实 DGN 后校验成员身份、当前公会、周期和前置；组队每个成员都必须通过，入场冻结归属，不允许出图时换公会转移奖励。
3. `dungeon_settlement_reward_owner.go` 向领域 `dungeon/settlement_owner.go` 传服务器确认的公会通关上下文。复用已有 `GuildSettlementUnitOfWork`：先锁 registry，再锁角色资产及 completion receipt，同一事务累计进度、结算奖励、写回执。专属副本不能冒充 `GuildOrdinaryClear`，该字段明确仅用于普通适正图 +10 积分。
4. 周期键须进入 completion 身份；重放旧周期、同次通关多成员重复贡献和提交失败都需独立测试。队伍贡献增量与双倍条件未定，不能先把所有结算都当 count+1。
5. 事务提交后向同公会在线成员刷新741，重登读同一持久快照。广播失败只补投影，不能再次发奖或累计。

奖励表已读到每图 `10154439` 的 3/4/5/5/4/7 个、contribute 20、重复奖励 `10156320×1`、周奖励最终图 8508。尚需确认 contribution 对应域、重复奖励资格和清算时机，故本单没有写入玩家资产。

## 守护神与公会战

匹配 NPC1500/1501 的 `[attend guardian]` 参数分别是 1/2。NPC 菜单 sender 分支 `0354D991` 从 role key 212 取参数，组装 CMD1350：

```text
u32 action=8, u32 guardianID, u32 0, u32 0
```

该分支到 `0354D853` 写最后字段并 flush；有限原生执行确认两个参数值的 16 字节请求。测试替换了 NPC role getter，没有运行完整 NPC 解析与菜单构建。字符串注册已找到 `[attend guardian]` 的 token 0x13d6，token 到 role key 212 的完整解析桥接仍待补证。

CMD1350 的 ACK 在 `010779C3` 注册到 `01067EF0`：成功分支直接返回，失败分支按错误码显示窗口。因此仅成功 ACK 不会持久化或显示已召唤的守护神。

公会战 NOTI1297 的 `01077450` 读取固定 2197 字节状态，比较守护神等级/技能并刷新公会对象和城镇 NPC；NOTI1337 的单 u32 进入 `010707C0`，所见路径是战斗结果/场景更新，不能把它当作召唤确认。完整状态布局、action8 的后续通知、重复召唤和重登契约未闭合。

`agitwar.etc` 两位守护神均列 AP=50000、GP=1000，但这些配置尚不能证明 action8 应立即扣哪种现有货币。先核清动作与消费字段，再新增扣费 owner；不能同时扣两项或拿普通贡献币代替。

V164 实际接收门控链的 34 个 class/opcode 观测表明：741/742 可接收；CMD1350 应答及所查公会战通知 777、778、779、784、1261、1280、1281、1283、1284、1293、1297、1337 均被拒绝。守护神闭环需要配套 EXE 精确门控变更及状态协议。先确认所需消息，再只放行这些消息并做全矩阵回归，按 EXE 发行→玩家通道→依赖服务端的顺序交付。

公会战后续还包含 8510…8520 地图、匹配/阵营/基地耐久/建设和胜负清算；真实 ETC 的 900 秒战斗时间、地下通路点数 300 和单人限额不能替代这一套状态 owner。本单没有启用公会战。

## 当前验证与完成边界

- 35 项有限原生契约通过，包含 Go 741 body 的原生消费；另完成 34 项门控观测。替换依赖为 PVF loader、STL/分配器、map 替换及 UI、NPC role getter、网络发送；原生 741 读取循环、count getter、完整开放/比例判定和 sender 分支实际执行。
- 8 个 Go 顶层专项、75 个子测试通过，0 跳过；包含真实提取目录及既有普通积分结算回归。无真实玩家过图验收。
- 当前仅交规则/编码候选，尚未完成首图实机进入、净化持久化、周期重置、奖励或守护神修复。后续冻结完整修复时需完成领域/bridge/control 全量、list/vet、双平台构建、隔离 MySQL 事务与并发测试，再提交上游修复 MR。
