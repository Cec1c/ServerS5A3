# 控制器默认启用 MySQL 批量写入

任务仓储保存状态时会在同一事务内替换角色的状态集合。仓储已有 `DNFBRIDGE_MYSQL_INSERT_BATCH` 开关，但未配置时逐行 INSERT。控制器会清理继承的 `DNFBRIDGE_*` 环境变量，外部 BAT 设置无法进入服务端；随着历史任务增加，接任务回包会明显变慢。

## 更新后自动生效

控制器现在默认向本实例服务端传入 `DNFBRIDGE_MYSQL_INSERT_BATCH=200`。新建实例和旧 `runtime/config/instance.json` 都不需要添加字段。按原有构建/更新流程更新服务端配套程序（包含 `DNF90Control.exe`），通过控制器重新启动服务即可启用；不需要替换客户端 EXE、PVF 或修改数据库结构。

仓库的 `build.bat windows amd64` 和 `build.sh windows amd64` 默认构建 Server、Control、Doctor，CI 也分别生成这些产物。仅替换 Server 而沿用旧 Control 的部署不会获得这个启动默认值。

可选配置 `database.insertBatchRows` 接受 0～1000：省略或 0 使用 200，1 回退到逐行写入，2～1000 使用指定批量。只有需要覆盖默认值或回退时才修改该字段并重启；删除字段会恢复 200，而不是逐行模式。配置仅作用于本实例，不修改系统环境变量或 MySQL 持久化参数。

当前累计线上控制器还支持启动级显式覆盖 `DNF90_MYSQL_INSERT_BATCH=1..1000`。合并时必须保留该兼容入口：有效值优先于 `database.insertBatchRows`，只影响本次启动；空值、非法值或越界值不覆盖实例配置，最终仍使用实例值或默认 200。原始继承的 `DNFBRIDGE_MYSQL_INSERT_BATCH` 继续被清理，不能作为绕过入口。

## 范围与其他启动入口

此参数影响所有使用既有 INSERT 批量器的仓储，包括背包、装备和任务；保留行集合、事务提交及失败回滚。现有占位符预算仍限制单条 SQL 的实际批量。

本改动只调整控制器启动入口，不改变直接运行 Server 的仓储默认值。自行编排的 Linux/Docker 或其他启动器需要由其启动流程传入已有的 `DNFBRIDGE_MYSQL_INSERT_BATCH=200`；Windows 的 `instance.json` 并不是这些入口通用的配置文件。已经设置 200 的部署脚本无需重复修改。

## 验证

隔离验证使用角色任务记录的只读快照，写入连接专属临时表并逐项比较状态。711 条状态三轮结果：逐行保存 778～805 ms，200 行一批为 66～68 ms，读回一致。修复前四次接任务收包至成功回包约 966～1022 ms；临时表数据仅代表隔离保存阶段，不是正式请求的完整耗时。2026-10-26，Windows 测试实例启用 200 行批次后，用户确认接任务不再卡顿。

默认化的控制器回归覆盖旧 JSON 缺字段、显式 0、1 回退、200/1000 覆盖、非法值拒绝以及继承环境隔离。仓储既有回归验证批量写入的数据等价和事务回滚。无需再次写入玩家存档来迁移配置。
