# START_MAP物体掉落行使用原生20字节布局

有物体掉落的普通地图在START_MAP的extra区域每行多写一个字节。客户端读取下一条时因此将前一条的末字节当作物体下标，后续序号、物品编号、数量和包尾字段错位。单行时也会将这个字节当作下一字段的雾效标志。没有extra行的地图不受此差异影响。

固定preview v141模块SHA256为26abf551753c2745c2e5b349fb24336422a189187ff847c995e0df9a68871079，START_MAP回调VA 0x1ff8d80，opcode29注册位于0x2001f81。实际extra循环为0x1ffbec0至0x1ffbf77，读取顺序如下：

| 字段 | 字节 |
| --- | ---: |
| 物体下标 | 1 |
| 运行序号 | 4 |
| 物品模板 | 4 |
| 数量 | 4 |
| 耐久 | 2 |
| 增幅类型 | 1 |
| 增幅值 | 2 |
| 扩展值 | 2 |
| 每行合计 | 20 |

下一个u8在循环结束后0x1ffbf84读取一次，是雾效标志。0x2621750构造器的最后一个flag由调用者传入常量0，不从线包读取。旧注释把循环外的u8归到了每行中，且旧地址无法用于当前模块，不能作为21字节依据。修复只移除原生u32布局中的这个多余字节；actor行仍为21字节，显式legacy-u16诊断布局保持历史19字节，掉落数量和资产事务不变。

当前stable v133模块SHA256为29a3f7f141841483f492e63834aac6c3f0eeb50baf373c0100ba6a3e33ec32b8，与已校验stable清单一致。两模块的extra读取循环、构造器和append窗口逐字节相同；本修复无需替换EXE或PVF。

原生离线回放运行实际读取循环，替代包读取叶子及物体构造/向量/析构叶子，检查读取宽度、构造参数、游标、雾效及栈平衡。0/1/4行边界和六份历史完整四行报文共18个对照：旧21字节的非空行按预期不匹配；20字节对照均正确。读取循环0x1ffbe93至0x1ffbf8c的249字节摘要为74533360e1d860a0b7de1a93aafbe190c8530c9ed02e7461cea8f29882369042。原始报文和反汇编保留在本地诊断目录，不进入源码。

独立Go消费者测试按照原生语法解析0/1/4行及完整雾效、载具和队员尾部，原代码失败，修复后通过。既有空集合、actor和legacy-u16用例保留。真实a56普通副本310/map36765及313/map33753各生成四条10158700时空石计划；已有313两条真实地图路线、START_MAP生成和拾取事务回归继续验证。地图/资源及内存仓库不代替原生玩家验收。

时空石10158700与精炼的时空石10158964是不同物品。旧独立掉落诊断覆盖后者，不能据此证明前者的地图物体掉落正确。本修复证明并修正extra行错位，不宣称已复现或完整解决玩家报告的四倍显示及重登数量回退；仍需实际客户端验收。
