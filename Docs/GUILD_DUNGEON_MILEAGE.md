# 普通地下城通关公会积分

本服规则：公会成员每次通关适正等级的普通地下城，为所属公会增加 **10 公共积分**。数值对应 PVF 的 `[Guild Mileage for Dungeon Clear] 10`；不同时增加个人 Mileage、红包贡献度或公会经验。

资格由服务端已接受的通关和进入时等级判断。优先使用 DGN 的推荐等级区间，旧脚本使用最低等级至基础等级；缺失或畸形区间不发放。根据真实 DGN 类型、特殊模式标签和已冻结的运行模式排除教程、训练场、公会地下城、塔、大会、深渊、团本、活动等特殊副本。普通房间的 START_MAP 模式值 2 本身不代表深渊，深渊判断使用已有请求解释与冻结的雾标记。

悲叹之塔按独立的 `tower of grief` 标记排除，绝望之塔继续按 `tower of despair` 排除；不把两种塔混为同一种玩法。标记检查覆盖 Flags、IntegerValues 和原始段，避免无显式 dungeon type 的塔被视为普通副本。回归包含普通副本正向对照，以及真实 PVF 中悲叹之塔首层与第100层的修复前失败、修复后通过。

每个成员随自身结算分别提交，不扫描队伍替未结算角色发奖。同会两位合格成员各完成一次，公共积分合计增加 20；不同公会分别入账。会员关系在事务提交时读取；未入会的通关也记录零积分结果，之后入会不能重领。

## 事务与回执

`GuildSettlementUnitOfWork` 在原角色结算范围上增加公会注册表和本次结算回执。MySQL 先锁公会注册表，再锁角色及其资产，经验、SP/TP、已有结算奖励、公会余额和回执在同一 SQL 事务提交。内存实现使用共享聚合锁与回滚。普通 `CharacterSettlementUnitOfWork` 不获得公会 Settings 权限。

回执使用现有 Settings 表的独立 `guild-clear:v1:<SHA256>` scope，摘要包含账号、角色和服务端完成事件键；每次通关独立保存，不使共享公会 JSON 随通关次数增长。回执不能随近期展示流水清理。相同事件并发、重试、重建仓储以及后续通关后重放旧事件都不会重复奖励；换会不改变旧回执归属。SQL 提交结果未知时保留错误，通过原事件键恢复，不自动改用新键补发。

升级前最后一次结算的旧回执会迁移为零新增积分，不追溯补奖。更早且没有持久回执的历史事件不支持导入重放；正常客户端不能指定服务端完成事件键。余额溢出、所有权不符和保存失败使整次结算失败，不单独提交部分奖励。

## 显示与验证边界

成功或回执恢复后向当前结算成员发送已有 NOTI70 权威公会余额；其他在线成员在既有公会查询／场景刷新时读取最新余额。本单元不增加 EXE 接收位。2026-10-17起，新通关同时保存kind3的747近期流水，和持久结算回执分别保留；不伪装为积分礼袋。

回归覆盖普通／特殊模式、进入时等级、会员归属、并发与重复结算、旧回执迁移、余额溢出、未知提交恢复、内存保存后失败和取消；一次性 MariaDB 覆盖最终回执 SQL 失败后的整体回滚、独立仓储并发和重建后旧事件重放。真实本服 PVF 核对参数及普通、公会、塔、训练场和团本样本。原生通关及 UI 显示验收单独记录。

本单元仍需集成当前线上累计源码，不能以旧候选直接替换线上。若与其他公会 EXE 补丁一起发布，依赖顺序保持：最终 EXE Release 双端同步，玩家实际更新通道验签并核对 EXE/PVF/dstr/NPK/profile，最后部署依赖服务端。源码提交、自动化验证、发布和实机验收分别记录。

2026-10-17：通关加分同事务记录747近期流水，使用原生kind3显示“通关公会推荐地下城 +10GM”；购买支出使用kind5及真实内容ID。重发和数据库回滚不多记流水。旧余额不反推虚构记录，既有未保存展示流水的历史通关不补造。
