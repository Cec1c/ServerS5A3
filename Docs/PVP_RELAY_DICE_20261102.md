# 自由决斗擂台骰子与出战流程

## 问题与修复范围

战斗模式 3 的房间能通过准备检查并发送开始通知，但原先将 C2S298/299 按普通对战处理，仅记录加载消息。服务端既没有擂台选人状态，也没有发送客户端需要的 class-0/112 骰子结果。客户端因此无法获得双方出战席位并进入擂台战。

新增 `pvp_relay.go` 管理模式 3：等待所有参战者完成加载，安排选人，向已加载的房间成员发送骰子结果；接收替补的出战申请并广播申请状态；当前选手被击败后选择下一位存活队友，保留对手席位，最后一位队友被击败才进入既有结算。晚加载的观战者收到包含双方明确席位的快照，重复加载不重新投骰子。退出房间或结算会取消选人计时器，过期回调也会核对房间、比赛及阶段身份。

现有普通对战、练习、三角色车轮战和房间人数平衡规则保持原有行为。模式 5 不在本次协议取证和修复范围内。

## 客户端静态证据

分析模块为 PE32，ImageBase `0x00400000`，大小 `111828992`，SHA256：

`f17d9289658664f1a61069f322ace28608d24f93f1af30f81698d534ab4a8484`

以下均为该模块的 RVA；不能套用于其他摘要的 EXE。

| 入口 | RVA | 已确认语义 |
| --- | --- | --- |
| 擂台模式判断 | `0x026103D0` | 房间战斗模式等于 3 |
| class-0/112 接收器 | `0x01C05910` | 读取分组数，每组读取出战席位、行数及各行的席位和 u16 点数；调用选人提交；存在多行时触发 `DICE_ROLL` |
| 分组出战席位写入 | `0x032F8F20` | 两组各保存一个席位；输入 -1 保留该组之前的出战席位，并记录存活选手用于后续状态处理 |
| 选人提交 | `0x032F4AC0` | 清理申请标志，进入状态 7 |
| 擂台准备状态处理 | `0x032FBD80` | 状态 7 准备出战对象，随后进入战斗状态 3 |
| 初始选人状态 | `0x032FCE21` | 状态 8 设置五秒选人倒计时，并按队伍整理候选者 |
| C2S112 发送器 | `0x032F4BA0` | 替补请求出战，报文为空；检查当前席位、当前出战席位及本地申请计时器 |
| class-0/113 接收器 | `0x01C05A40` | 一个有符号席位字节；切换该席位申请标志，本人的申请消息更新本地倒计时 |
| 申请倒计时 | `0x032F4C80` | 根据申请状态设置五秒/二十秒提示与计时器 |
| 普通超时发送分支 | `0x0333FBCE` | 擂台模式跳过 C2S56，不能沿用普通对战超时直接结束整支队伍 |

class-0/112 的线上布局为：

```text
group_count: i8
repeat group_count:
    selected_seat: i8        // -1 保留之前的出战席位
    row_count: u8
    repeat row_count:
        seat: u8
        score: u16le
```

请求与通知使用不同编号空间。C2S112 是空体的出战申请，class-0/112 是服务端发出的选人结果，class-0/113 是申请状态通知。C2S58 是战后统计报文，不是投骰子请求。

五秒选人窗口和 1～100 的无重复随机点数是本次服务端选择策略。客户端证据确认了初始五秒显示、u16 点数的读取及展示，不证明官方服务端的随机分布或全部申请时序。服务端修复本身不修改 PVF 或玩家原文件；所需的客户端改动见下一节。

## 客户端接收门补丁（v2.0.8）

服务端修复上线后，玩家客户端 v2.0.7 仍然收不到骰子。它的接收门把 class-0/112 和 class-0/113 都判为丢弃，报文到不了上表的接收器，所以服务端发出的骰子结果和申请状态都没有效果。擂台赛必须配合 v2.0.8 客户端使用。

| 项目 | 值 |
| --- | --- |
| 输入 v2.0.7 | `eca5ae9017176fb159ae22d6498b2a6805b8b93295042363a90f37f2daae7a03`，112549888 字节 |
| 输出 v2.0.8 | `c6adcdffe2973ff02d524c1287ae952458857a55ef16947484d2215c43d392ca`，大小、入口、节布局不变 |
| 接收门 | 接收入口 VA `0x025239A0` 读取 `[edi+1]` 的 u16 编号后，在 `0x02523A13` 调用 `0x06F20400`；返回 1 放行，0 丢弃。`[edi]` 是类别字节 |
| 改动 | 把 `0x02523A13` 的调用改指向 `.bp0` 空余区里一段 37 字节的辅助代码（VA `0x06F20550`），同时更新 `.bp0` 的虚拟大小并重算 PE 校验和，共 37 字节 |
| 辅助逻辑 | 只有类别 0 且编号为 112/113 时直接返回 1；其他报文一律跳回原接收门，判定与原版逐字节相同 |

- 补丁已并入[本地客户端补丁栈](../scripts/client/local-patches/README.md)（`patches/pvp_relay_gate.py`）。`apply_stack.py --input <上游> --output <新文件>` 按调用点和辅助代码特征判断是否已打，不覆盖输入，不允许任何未声明的字节改动。2026-11-04 从 V207、V208 原版重新生成，结果与 v2.0.8、v2.0.8.1 逐字节一致。原 `scripts/client/patch_pvp_relay_gate_v208.py` 已移除。
- `scripts/client/local-patches/verify/verify_pvp_relay_gate.py --base <上游> --candidate <我方版本>`：在映射后的 PE 镜像上执行真实的接收门，覆盖类别 0～2 × 全部 65536 个编号，共 196608 种组合。要求没有执行错误，且只有 (0,112)、(0,113) 从 0 变为 1；控制组 (0,44)、(0,45)、(0,561)、(0,110)、(0,252)、(1,112)、(1,113) 不变。这只是接收门的静态检查，不运行游戏。
- 发布：2026-11-03 14:40 已作为 v2.0.8 发布到 90CN 的 DNF.exe 更新通道，当天经实机验证可用。EXE 本身不进仓库，以 Release 附件分发，见[客户端发布与上线顺序](CLIENT_RELEASE_SYNC.md)。
- 换新版客户端时：先跑 `apply_stack.py --check`。接收入口或接收门地址变了会报 `incompatible`，这时要在新版上重新定位接收门，确认 112/113 是否仍被丢弃，再迁移补丁；否则擂台赛骰子会再次失效。

### 上游 V208 合并版（v2.0.8.1）

上游 V208 在 V207 的基础上只改了文件偏移 `0x6A92366` 的一个接收位图字节（`01` → `07`），开放 817/818 两个报文，用于深渊史诗碎片商店。它和本补丁改的不是同一处：辅助代码只额外放行 112/113，其余报文仍交回原接收门判断，而原接收门用的正是上游改过的那张位图，所以两个改动可以直接叠加。辅助代码的地址和内容与 v2.0.8 相同。

| 项目 | 值 |
| --- | --- |
| 输入（上游 V208） | `5ce2ce3f01dacd05a6ce542d088911cc4fceb0f44ffa85dfa3a0886339e7cb5c` |
| 输出 v2.0.8.1 | `58b7c5e61435df2ccdd30dce412a33c213943a530e492d27656135fa6d735fc2` |
| 与 v2.0.8 的差异 | 只多了上游那个字节，以及随之变化的 PE 校验和 |

各版本的输入、输出摘要登记在 `scripts/client/local-patches/stack.json`。

接收门比对结果：
- 上游 V208 → v2.0.8.1：196608 种组合中没有执行错误，只有 (0,112)、(0,113) 从丢弃变为放行。
- v2.0.8 → v2.0.8.1：只有上游开放的 817/818 在 3 个类别下从丢弃变为放行。

以上都是静态检查，v2.0.8.1 的实机验收待完成。817/818 需要配套的服务端碎片商店代码才会用到；服务端还没部署时多放行这两个报文也没有影响。

版本号的说明：网关标签 v2.0.8 和上游 Release 的 V208 只是号码相同，内容无关。我方在上游版本上派生的版本，在后面加小版本号（v2.0.8.1、v2.0.8.2……）。
