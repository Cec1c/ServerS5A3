# 强化券对已穿戴装备的拒绝提示

对已穿戴装备使用强化券时，原生发送器已经识别目标属于穿戴容器3，却继续发送class1/op80（0x50）。请求开头实际为u8模式、u8容器；普通服务端解码器把这两字节视为u16模式，只接受0/1。容器3于是触发畸形模式拒绝，错误码4又被原生结果回调显示为“缺少物品”。不能按装备模板ID或重叠槽号去猜目标，否则背包中存在同模板装备时可能误判。

## 修复

`scripts/client/patch_upgrade_equipped_warning.py` 在原生目标查找完成后、材料查找与网络发送之前检查已解析容器。只有目标查找成功、容器3且模式0/1被拦截，复用既有原生弹窗和dstr文本：

- 强化：1651，“无法强化穿戴着的装备”。
- 增幅：21302，“无法对穿戴中的装备进行装备增幅。”

真正缺失的目标、背包装备、其他已解析容器和模式2..5继续执行原材料查找及后续路径，不更改成功率、费用或券的适用条件。拒绝分支没有发出强化请求，因此不产生服务端扣券或装备写入；不自动卸装。

原生调用方还会把普通false解释为1659“正在使用物品栏”，形成第二层弹窗。新拒绝分支保持AL=false，用EAX的高位标记已显示提示；两处已核对的券调用方仅对该标记跳过重复弹窗。增幅券仍执行原失败清理，清除选择并回到空闲状态；强化调用方保留其已保存的EBX与原返回路径。其他调用方仍读取false，普通忙碌、其他失败和真实成功保持原分支，不把拒绝伪装成已发送成功。

工具只接受核对过的官方累计V207、本服已验收的同代累计输入及上一版提示候选，生成独立候选，拒绝未知、截断、篡改和重复应用。利用原RX节已核实的填充范围存放守卫及两个调用方跳板，修改一处发送器跳转、两处调用结果分支、该节VirtualSize及PE校验和；节数量、权限、文件大小和其余累计功能字节保留。上一版输入另校验已安装守卫的完整字节。原通知结构不改。

## 原生证据

匹配官方V207及本服同代映像的VA：

- `0x25FDAB0`：强化/增幅发送器入口。
- `0x25FDB58`：背包查找失败后解析穿戴目标，栈槽`EBP-0x6C`为目标容器，`EBP-0x70`为目标槽。
- `0x25FDB6F`：本次守卫位置；未拒绝时原样调用材料查找`0x25ECE10`，回到`0x25FDB77`。
- `0x25FDB09`：既有dstr查找及原生模态弹窗路径，最后返回失败，不提交请求。
- `0x17F3C2A`、`0x331234E`：两处调用方的结果处理，原false路径弹出1659；增幅拒绝继续到`0x3312375`清理，不进入`0x3312441`的状态2等待路径。
- `0x3E72CE4`：原安全cookie检查保持EAX；整段原生调用方回归执行实际比较和返回，核对标记、AL=false、栈与非易失寄存器。
- `0x25FE0E5`：原发送分支；`0x1FE02A0`结果回调的错误码4分支查询dstr1658“缺少物品”。

离线原生回归从实际发送器入口执行背包/穿戴解析，并运行增幅调用方整段控制流，覆盖上一版21302后再弹1659的失败对照、新版仅一次提示、选择清理、连续拒绝/普通失败/成功、强化调用方返回栈/非易失寄存器、背包和其他动作保留、精确修改范围及输入校验。会话查询、物品查找、dstr和重量级UI叶子为明确适配；调用方回归使用真实安全cookie代码，发送器局部检查的cookie为适配。离线回归不等同完整游戏GUI或实际扣券测试。可选精确dstr夹具验证两条原生文案，无需改dstr。
