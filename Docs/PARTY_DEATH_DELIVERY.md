# 队伍死亡通知投递

击杀者持有自己的副本锁时，原死亡广播逐个等待队友的网络写锁与写入预算。一个不读数据的队友可以使击杀者和后续收件人等待整个写预算。死亡通知现交回收件会话的串行事件循环，继续使用原有传输编码和写入上限。

每个连接只有一个死亡通知待发队列和最多一个重投定时器。事件队列满时保留通知，25毫秒后重试一个唤醒事件；每次唤醒只处理一帧，随后重新排到普通事件队列尾部。待发上限为512项及1 MiB，不能通过无界协程或无限字节缓存掩盖持续拥堵。达到待发硬上限时关闭该收件连接，使不完整的场景流退出；其他连接和已提交的角色数据不受影响。

每项在入队前复制已生成的收件方通知体，并保存角色身份、代次、源房间对象、收件方场景对象和副本实例。真正发送时，在收件方副本锁下重新核对这些条件及实例中的成员登记。队列唤醒本身不绑定某个旧角色代次，否则旧唤醒被框架提前丢弃会使新代次待发项失去消费者；每项通知仍须通过完整身份校验。新代次入队会移除旧代次积压，并用版本号防止在途旧项清理新队列。

待发队列的锁只保护队列元数据，不跨网络写入、仓储操作或事件投递。入队的身份检查会短暂获取服务会话登记锁，调用方不得在持有该登记锁时调用投递入口。真正的发送由收件会话持有自己的副本锁，核对实例登记后释放实例锁再写网络；发送方不会获取收件方副本锁。

死亡帧写出成功后才标记该收件场景的敌人死亡。任务材料投递和最终房间结算在释放收件方副本锁后沿用既有入口；结算另外绑定同一房间和场景，防止排队期间切图后结算新房间。原死亡响应缓存、重复请求幂等、经验提交和掉落事务保持各自所有者。

选角日志的 `projection_*_ms` 是同步投影函数的总耗时，可能同时包含读库、准备及发包，不能解释成纯SQL或纯socket时间。字段只附加到原有的一条相关慢样本，继续使用既有限流；`batched=true` 时投影通常早于ACK真正flush，必须结合 `ack_written`、`ack_write_ms` 和总时长判断。尚无这些新增字段的现网测量时，不能指定某个投影就是选角延迟的根因。

回归使用真实会话事件循环、`net.Pipe` 不读收件方、共享副本夹具和既有协议/经验/清房测试。隔离证明只覆盖上述服务器机制，公网时延和客户端实际显示仍需上线后验收。
