### 失败回包与客户端等待状态（本席复核）

713 处理器 0x1faee80 的失败分支：`01faee84 cmp byte ptr [ebp+0xc], 0` → `01faee8e je 0x1faeeca` → `01faeeca/01faeece call 0x37e82e0`（只把 error 字节读进栈上局部 [ebp+0xf]）→ `01faeed6 mov esp, ebp; ret`；该局部此后**没有任何读取**。714 处理器 0x1faeee0 是同一形状（`01faeeec cmp byte ptr [ebp+0xc], bl` → `01faeeef je 0x1faef27` → `01faef27..01faef30` 同样只读一字节后返回）。

两个处理器里**没有**任何全局/UI 写（只有成功分支写 `item+0x2aa`），也没有超时或 pending 标记；上行侧 0x32d3767（713）在写体之前只调一次 0x1a685c0(1,3,0xd)（构造 6 字节结构后调 0x1a68000 的 UI helper，与回包无回调关联），0x32d3746（714）没有这类调用。

结论与边界：服务端对 713/714 的失败**不回包**不会让客户端停在等待状态，最坏情况是玩家看不到错误提示、图标保持原样（服务端也确实没改）。90CN 也没有已证的 sort-lock 错误码枚举（A21 的 17/19/21/22 只属于 267/268/269 资产锁，不能挪用），而客户端又把该字节丢弃，因此本实现不臆造 `0 + error`。原生验收建议：对服务端会拒绝的目标点一次锁定（例如界面允许的 0:354 共享晶块格），确认没有卡住即可；这条是 GUI 观察项，不是源码可证项。

### 7.1 根因在客户端侧（本席独立复核，离线）

下发客户端在**入站接收函数**里先做 opcode 准入判定，再按分类分派：

| 位置 | 证据 |
| --- | --- |
| 接收入口 0x25239A0 | `02523a05 movzx ecx, word ptr [edi+1]`（opcode）→ `02523a13 call 0x376E6C0` |
| 准入谓词 | 0x376E6C0 头 6 字节 = `jmp 0x6E83610`（.rebuild 段）；0x6E83610 = `movzx eax,[esp+4]; cmp eax,0x5c2; ja→0; bt dword ptr [0x6E92300], eax; setb al; movzx eax,al; ret 4` |
| 位表 | VA 0x6E92300，188 字节 ≈1474 位，**按 opcode 一维索引，没有 class 维度**；opcode > 1473 恒 false |
| 判定消费 | `02523c8a mov al,[ebp-0x5d]` → `02523c94 cmp al,1` → `02523c96 jne 0x2523F47`；0x2523F47 只 `mov eax,1` 返回，**不分派也不报错** |
| class 分支在其后 | `02523c9c movzx ecx, byte ptr [edi]`：0 → 0x2523E95（class0/NOTI：`02523f08 movzx eax,[edi+1]` → 查全局表 0x57BD2A0 → 0x251E340 派发）；1 → 0x2523CF6（class1 命令路径） |

位为真的既有 class1（267/268/269）也有 class0（13 整容器页、251），说明同一张表同时管两类；因判定在 class 分支**之前**，class0 通知与 class1 命令同受门控。713/714 的位在 v101（1ac12645…）与 v96（8bf1d39d…）**都是 0**，所以上一轮实现的 class1/713、class1/714 ACK 从来没被派发过；客户端 0x1FAEE80/0x1FAEEE0（注册点 0x1FBA1EE / 0x1FBA201）根本没跑，item+0x2aa 不被写，图标只能等重选角色时由登录整表 op13 的 0x77 行 0x60 投影出来。

对黄锁（class0 通知）：0x00FB(251) 锁列表增量位为真，0x00FC(252) 解封通知位为**假** → 该 NOTI 同样被丢弃。本轮不扩大客户端放行（252 保持 0），只报告。
