# 交易 offer 投影写失败收尾

## 边界

当前 R56 现场已证明双方两条 op15 均以 119 字节、trade slot 3 发出，随后双方 op17/state1、两次 state3 和双方 op18 均出现。该日志不能证明客户端已经绘制交易行，因此“锁定后看不到对方物品”的 GUI 根因仍等待 native。

本补修处理的是一个独立的安全/一致性缺口：会话里已经保存的 offer 或金币，可能因为随后的写包失败而对一方不可见，却仍能进入双方最终确认并成交。

## 原故障路径

物品新增、物品删除、金币新增、金币删除四条路径都先在内存中改变交易，再分别发送：

1. 发起方 class1/op19 成功 ACK；
2. 对端 class0/op15 增量。

原实现任一写失败都直接返回，不撤销已经改变的交易状态。失败后的交易仍保留在双方索引中，客户端后续 state5/state3 可以继续把它提交。

## 修复

只在这四条路径的 ACK 或对端 op15 写失败时调用现有取消路径：

- 清理双方交易索引；
- 按各自当前 offer/金币生成既有 op16 取消；
- 向双方在线连接各尝试发送一次；
- 返回原始写错误；
- 不发送 op18，不提交资产，不构造未知快照。

成功路径的报文、顺序、slot、数量和成功 ACK 未改。

## 回归

新增 item_trade_visibility_failure_test.go，共 16 个子场景：

- 物品 add/remove；
- 金币 add/remove；
- offerer 或 peer 作为 sender；
- 发起方 ACK 写失败或对端 op15 写失败。

每项都验证双方索引为空、双方各一次取消、无完成包、后续 state5/state3 不能成交，以及仓库晶块或角色金币未变化。

旧生产文件下 16/16 红，补修后 16/16 绿。后续完整检查另以本地回执记录。

## 未覆盖

- op15 已成功写入 socket 但客户端未接收或未绘制；
- 锁定状态变化时客户端是否清空交易行；
- 网络写成功之外的消息丢失；
- 并发 ready 与 offer 变更之间的竞态窗口。

这些需要 native 或进一步现场证据，不在本次补修内。
