# 当前客户端队伍成员身份的等级/职业顺序

## 静态证据

固定生产映像 SHA256 `735ed3e96f178bd2b546be18ff38ba4a578c951092b1d97a352ab73db7333d8b` 的 NOTI9 处理器为 `02016350`。跨上下文成员身份的前五字节由 `02016BC1..02016C02` 读取。前两字节分别存入局部变量 `[ebp-368]`、`[ebp-381]`。

在没有现存 wrapper 的分支中，`02016F53` 创建 wrapper，`02016F67` 取得其 profile。`02016FC3` 将第一个字节交给 profile `+14` 的编码等级存储；`02017037..0201703E` 将第二个字节直接写到 profile `+4`；之后 grow/awakening 写入 `+8/+C`。

profile `+4` 用作职业：`022BE74D..022BE761` 取 `+4/+8` 参与已有 actor 类型检查，缺失 actor 时 `022BE81C..022BE825` 又把它们交给角色创建路径；`00C5FD4A..00C5FD5E` 与 `0345F60E..0345F632` 等调用点也将 `+4` 按 `0..15` 职业表索引使用。它不能承载角色等级90。

服务端两个组包路径此前均将成员身份写成 `job,level,grow,...`。因此旧包在原生新建 wrapper 路径中把等级写进职业字段。已有 wrapper 走另一条路径，不执行上述新建身份赋值；这解释了为什么相同报文内容不必造成所有接收者相同结果，但仍不是对特定现场分支的动态命中证明。

## 修正范围

- `official-24.9` 的通用成员表改为 `level,job`，覆盖普通 kind0 和保留队伍 kind2。
- 独立的副本初始房间槽位表使用相同写入函数，避免只修补发路径而漏掉首次组包。
- actor 头部是另一种布局，不交换其中字段；同频道无内联身份路径保持；旧 vendor profile 保留原字节顺序。
- 不增加消息、不重放复活、不改变HP、队伍槽位、成员关系或奖励资格。

此次现场的初次四人名单摘要在不同接收者间一致，因此没有证据把“某个接收者数据库读取失败后使用默认职业”定为这次原因。该默认值问题另记，不在本项夹带修正。
