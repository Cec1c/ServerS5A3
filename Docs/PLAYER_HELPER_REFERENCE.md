# 玩家内辅参考方案（供参考，默认关闭）

本贡献集中整理下游内辅开发中可复用的服务端事务、Windows 插件宿主及客户端适配经验，便于上游评估或择取。参考代码在 [`tools/player-helper`](../tools/player-helper/README.md)，作为一个 S5A3 Draft PR 提交。

## 功能与职责

| 功能 | 实现与限制 |
| --- | --- |
| 自动拾取 | 金币独立开关，装备/消耗品各七档品级；仅拾取当前角色合法拥有的掉落。背包失败暂停，成功公告后立即唤醒，每轮最多 64 个后让出 owner |
| 出售/分解 | 按品级预览并确认；排除锁定、穿戴和强化等受保护物品；复用 NPC/分解事务，分解采用当前合法机器、费用和耐久，不回退为免费分解 |
| 修理 | 使用真实装备、PVF 耐久和原有价格；预览不扣费，提交重新核对；穿戴装备通过专用投影刷新 |
| 金库 | Alt+F 调用固定客户端的原生金库窗口；存取沿用游戏原生交互和服务端协议。保留服务端受限仓库事务接口供参考 |
| 过图 | Alt+方向键选择当前已清房间的合法相邻门，复用服务端导航；队伍由队长发起，保留队员及过门检查 |
| 插件宿主 | Ctrl+Z 面板、前台热键、进程身份校验、独立插件生命周期和签名校验。生产宿主启动后固定插件与配置；SDK 重载仅用于生命周期验证 |

资产写入、数量、价格、归属、装备状态及地图判定都由服务端负责；宿主不直接连数据库，也不持有 GM 凭据。服务端扩展仍分别位于 dnf 域事务与 dnfbridge 传输/当前客户端兼容层。

## 默认关闭与会话接入

1. 服务端显式设置 `DNFBRIDGE_PLAYER_HELPER_REFERENCE=on` 才开放 `/api/account/helper`。自动拾取还需要 `DNFBRIDGE_HELPER_AUTOPICKUP=on`。账号 API 保持原有 loopback 绑定。
2. 采用方的既有 HTTPS 网关显式转发 `POST /api/account/helper` 及 `X-DNF-Helper` 到账号 API，保留请求/响应体及状态码；按宿主超时和响应大小限制接入。这个 PR 不包含网关部署或私有登录器。
3. 登录器正常取得短期游戏登录 token 后，仅在内存派生拾取能力 `SHA256("Arad-Helper-Loot/1\n" + token)` 和便捷操作能力 `SHA256("Arad-Helper-Player/2\n" + token)`；服务端保存能力摘要并关联实际已登录角色。不能通过请求参数选择账号、角色或 PID。
4. 将 `integration/LauncherSessionPublisher.cs` 编入已有 `DNF90.Core.exe`，启动宿主后调用 `PublishAsync`，传入相同根目录、实际游戏进程、短期 token、HTTPS 网关基础 URL 与证书 SHA256。示例使用同用户命名管道、4 字节小端长度、至多 4096 字节 JSON 和成功回执。宿主验证发布进程为自身目录的 `DNF90.Core.exe` 且处于同一 Windows 会话；其他登录器命名/目录需先协调修改身份校验。
5. 宿主按 PID、创建时间、完整路径、文件摘要区分实例；切换前台窗口后重新关联角色，PID 重用或游戏退出会撤销旧绑定。HTTPS 禁止代理/重定向，并校验证书固定摘要、有效期和主机名。
6. 将 `config.example.json` 复制为 `<root>/helper/config.json`，自行签名并放置插件后显式选择 `EnabledPlugins`（`autoloot`、`utilities`）及品级。源码默认不启用插件或筛选。宿主通过 `Arad.Helper.exe --root <root>` 启动；发行者仍需设计自己的安装/更新接入。

能力值不应进入日志、状态文件或发行清单。示例公钥与生产信任根分离，不包含发行私钥、玩家数据或运行配置。

## 已整理的通用问题与实现经验

- **短暂网络异常不能永久停拾取，也不能恢复手动停止。** 租约为 15 秒，宿主每 5 秒续租；超时保留筛选与同一 owner/revision，恢复时重试同一申请。角色改变、背包暂停、显式停止及其他 owner 接管均要求重新操作。
- **异步旧任务不能覆盖新一轮状态。** 角色代际、插件代际、调度 serial、owner、lease、revision 与递增续租序号分别限制生命周期；退出、重登和停止撤销旧任务。掉落消息写成功后才唤醒拾取，owner inbox 满时不阻塞共享时钟。
- **资产预览不是提交授权。** 出售、修理、分解及仓库操作在 owner 内执行，短期 plan 绑定角色和快照；仓储事务提交前再次核对，变化即要求重新预览。重复 request ID 返回已有回执，避免重复扣费。领域新增的快照回调仅负责验证，不发送消息或外部副作用。
- **穿戴列表不能当作普通背包刷新。** 修理后的 list 3 走穿戴装备投影；普通增量物品刷新拒绝 list 3，防止客户端把装备显示移除。扣费与耐久提交完成后才刷新，显示失败提示重登且不再次执行交易。
- **快捷键只在匹配前台游戏消费。** 用户界面、文本输入及键盘路径的进一步验证需在 Windows 夹具和对应客户端完成。原生金库仅有固定窗口操作，不能推广为任意内存调用。

## 原生适配与验证边界

`Processes.cs` 和 `native-ui` 当前共同限定 EXE SHA256 为 `bb7022670b546ab200bc6f9718a47e51ff1e8cc78b4049231229db72b6aa3552`。窗口号、调用约定及地址见 [原生组件说明](../tools/player-helper/native-ui/README.md)。上游若采用另一 EXE，应重新取证、适配并验证，不能关闭摘要校验来获得兼容。

`build.py` 将源码复制到独立输出目录，记录逐文件摘要，编译 SDK/宿主/登录器示例并执行 SDK 夹具。可选 Zig 构建原生 x86 DLL、broker 和假游戏进程，不执行真实游戏。服务端测试使用内存仓储与固定 PVF 夹具，覆盖鉴权、租约、掉落归属、事务回滚、快照变化、幂等、机器费用及穿戴修理投影。

本参考分支的验证结果以 PR 为准。下游已有实机使用经验，但提取后的登录链路、Windows 热键/界面、原生金库 hook、队伍可见状态和最终发行包仍需采用方验收；本 PR 不创建 Release、不更新玩家通道、不部署服务端。
