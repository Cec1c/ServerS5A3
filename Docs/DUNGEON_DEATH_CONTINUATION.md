# 连续死亡请求接续与深渊碎片等级索引预载

怪物死亡通知已经发出后，下一条死亡请求仍可能在当前经验事务提交期间排队。原先只在开始处理前收集完整请求，无法接纳第一只怪处理过程中刚到达的下一条请求。深渊尾怪还可能首次构建碎片等级索引，把装备脚本扫描放在死亡通知之前。

## 连续请求处理

当前版本的普通副本死亡处理在同一会话事件内，处理完现有死亡请求后、提交待结算经验前，再非阻塞检查已经到达的读块。接续请求仍逐条经过原命令处理、角色与房间校验以及替换登录检查；死亡通知、任务和掉落仍按原先顺序执行。

- 每个事件最多处理32条死亡请求，接续读取最多16个读块；没有已到达字节时立即提交，不增加等待窗口或异步奖励。
- 遇到其他指令即停止接续，保持报文顺序；半帧、错误帧及EOF交回原收包流程。
- 只有同一角色、代次、房间还有普通怪经验待提交时接续。升级、清房和特殊对象按原入口先提交经验，随后停止动态接续。原先已拆出的固定请求段保持既有处理方式。
- 通知写失败、替换登录或后续命令失败时，仍提交此前已接受击杀的经验；失败事务不发布预测属性。
- 新接续帧使用本次拆包完成时间记录分派等待，避免把其到达之前的处理时间算入等待。

经验公式、升级奖励、满级熟练度、冒险团与成长胶囊的事务边界保持。每只怪的任务、任务物品和普通掉落继续调用原实现，称号指令保持原顺序，宠物饱食度及成长保持原来两个事务。组队沿用共享实例权威死亡和重复报告重放逻辑。

## 静态资源预载

把深渊碎片等级索引加入监听前的静态表预载，直接装入实际怪物目录使用的原缓存。关闭等级带的legacy模式跳过该项。保留原错误缓存及可选表降级，不消费随机数，不改变候选顺序、等级窗口、概率、个数或归属。

这只提前构建等级索引；选中碎片后其他资源解析仍可能首次读取。数据库提交已经开始后才到达的请求也仍需等当前事件完成，因此不能据此保证所有死亡通知都无延迟。

## 验证范围

新增固定请求段与动态接续的对照：在第一条死亡通知之后注入第二条请求，验证接续模式在经验提交前确认两只怪，未满级及满级最终累计与原规则一致。

覆盖真实收包循环、组队双端死亡广播及队员重复报告、升级、清房、混入其他指令、半帧、坏帧、EOF、32条上限、16读块预算、替换登录和通知写失败。碎片预载验证原索引与预载索引内容一致，释放PVF文本缓存后反复取索引不新增脚本读取。完整测试、真实PVF专项和正式构建的执行结果另记验证回执；实机收益需安装后确认。

真实PVF用例结束后清理仅属于该归档的静态缓存引用及可重建文本缓存，保留其他来源缓存。胶囊用例继续检查原经验与胶囊数值，并在失败时输出隔离事件日志；测试夹具释放不进入生产程序，不放宽业务超时或断言。
