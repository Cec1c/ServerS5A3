# 超时空已入图成员的已有编队恢复

两名成员由正式遭遇战入口一起入图时，服务端已经创建managed party并冻结参与者。当前op10 mode0/12此前无条件拒绝active邀请，导致这类成员再次请求组队也收到失败，而op11已支持同encounter恢复。

本次只为op10补同一已提交队伍的恢复：核验每名成员当前角色代次、raid/run/参与者及实例owner，并要求真实加载后记录的partyRun键一致且匹配各自当前场景。成功回既有class1/op10 `01`，然后沿既有副本名单153/9刷新。没有邀请登记、新建队伍、class0/op11握手重放、场景切换、ready写入或资产/奖励修改。

这不是活动遭遇战之间的新建/转移协议。两人各自在不同run时保持原拒绝，不能仅将partyID改成相同而保留互相冲突的怪物/掉落/死亡与奖励账本。当前不同区域真实独立入场控制已明确区分这一未实现范围；D03用户现场是否属于该情形尚未证明。

真实PVF定向：设置DNFBRIDGE_REAL_PVF_SMOKE后运行 `go test -buildvcs=false -count=1 ./internal/services/dnfbridge -run '^Test(R159FiendWar|R134N1RealPVF)'`。未选择资源沿既有helper跳过；显式坏路径失败。覆盖普通开放区域、纯白4953/暗黑4978，mode0/12重复请求及后续op11、身份/场景/未ready/退出/结算拒绝、ACK及名单写失败后再次请求。纯白/暗黑测试的战场boss解锁状态为受控fixture；入场、运行时共享及op37加载处理是真实handler，没有伪造ready。

原生证据复用D153/D154：class1/op10成功consumer读01后结束；失败03对应当前配套dstr“对方已退出游戏”。v151发行收据只新增1342接收适配器。名单/P2P/GUI终态没有因此得到实机证明，不宣称用户“连接中”已经消失。
