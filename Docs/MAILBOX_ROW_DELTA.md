# 邮件记录按差异保存

邮件状态、附件和元数据仍属于原来的邮箱聚合与资产事务。正常 MySQL 保存先更新并锁住邮箱父记录，然后在同一个物理事务内读取写分片上的四张子表，对比待保存聚合，仅执行必要的邮件、元数据和附件行增删改。通用 `Save` 无须先 `Load`；同事务多次保存、多个仓储实例以及旧写者介入均重新比较实际状态。

读信只更新邮箱父记录与该封邮件的头部。领取会保存已读/领取/删除状态，并真正删除已经转移的附件及其扩展属性。新增邮件使用普通 INSERT，省略的邮件及附件仍会删除。原有事务、归属检查、领取编号、历史高水位和回执继续生效，不新增数据库对象或后台任务。

## 兼容边界

- 清空整箱仍直接批量删除，避免逐封处理造成反向退化。
- 非物理事务的兼容 SQLDB 实现保留原完整替换路径。
- 孤立元数据/附件、稀疏附件下标、无法由原聚合读取完整表示的空 BLOB，继续完整替换，确保历史修复会清除隐藏行。
- 新元数据或扩展键使用 INSERT。数据库排序规则认为相同的两个不同 Go 键仍报唯一键冲突，不能通过 upsert 吞掉错误。
- 附件 raw_entry 的 NULL 与空 BLOB、字段值、邮件映射键与附件顺序保留原保存行为。
- 保存前读取失败直接返回，外层事务回滚。此优化没有为无事务的旧“先读后保存”调用增加并发合并语义，完整聚合覆盖语义保持。

## 对原优化建议的采用结论

采用邮件行和子记录的差异写入。保留完整可写 `Mailbox.Load`，不直接加入“仅未删除、未过期邮件”的过滤条件：发信的 `nextMailID` 扫描全部父信编号，`ensureMailboxClaimIDs` 也需要历史领取编号和高水位。过滤后再保存会误删省略的历史记录，并可能使编号重新分配。已删除/已领取信的遗留附件修复也依赖完整读取。未读提示已有独立窄投影 `MailboxUnreadReader`，不读取正文和附件。

本次没有实现跨请求邮箱缓存或把数据库持久化改为异步。只读列表可以另行设计独立投影，但不能用部分视图冒充当前可写聚合。

## 验证范围与成本

真实隔离 MariaDB 对参数插值开/关分别比较完整替换和差异保存，逐表核对实际持久化行，包括读信、领取、头部修改、元数据、附件、删信、发信、清空和空 BLOB。另验证孤立行修复、排序规则冲突、每条写入及四次读取处失败的真实事务回滚、同事务反复保存、旧写者插入、另一收件人隔离和提交后重新读取再保存。

80 封信的合成工作集（每封两件附件、三条附件属性及两条邮件元数据）中，读信从 645 次写入变为 2 次，领取从 640 次变为 6 次；非空保存增加四次读取。清空仍为 5 次写入，不增加读取。这里统计 SQL 执行次数，不是受影响行数；单次隔离计时不能外推为整服吞吐或高峰延迟改善比例。使用现有连接与锁顺序，无生产测试或部署。
