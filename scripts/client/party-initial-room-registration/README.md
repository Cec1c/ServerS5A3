# 首次落位通知的现代队伍房间登记候选

输入固定为 SHA256 `244b5c1e3126967d8a2b718658c586c1ac675a08b255d7377e95b93b4b815112`。
此目录是离线生成配方，不包含 EXE、玩家资料、原始报文或机器配置。

当前客户端在 `2001fc3` 将 `1ff2ec0` 注册为通知 120 的处理器。
该处理器先检查控制器 `+C0` 的模式谓词，再从旧全局 `57b9080` 取队伍。
本地复现中的现代副本场景类型为 3，但旧模式值为 1、旧队伍为空；
活跃成员由 `56a3768` 管理，实际房间由 `2524fb0` 选择。
四组用户报告的不可见对象均存在，却不在实际房间注册表中，且对象 `+A8=0`、`+C8=0`；
可见对象的 `+A8=111h`、`+C8` 指向实际注册表。这个后期快照不能单独证明最初收包时的状态。

候选在原槽位边界检查后增加受限分支：旧队伍必须为空、实际场景类型必须为副本，
目标必须是活跃槽位内的非本地角色，资料状态与队伍路由必须为 1，
目标与本地角色必须绑定同一队伍记录，槽位 UID 和 owner 必须匹配。
已有登记直接结束；只有登记类型为 0、所属注册表为空的新对象才调用原生 `288a260`。
其它情况回到原处理器。不会重放复活通知、调用 HP/MP 重置或重建角色对象。

v3 实机仍复现：四个客户端各执行七次候选入口，全部回退，未调用补登记；
稍后的现场只读副本已能通过队友登记条件。精确失败条件仍未捕获。
v4 在经过相同身份校验的本地角色通知上增加一次就绪检查：本地角色必须已在实际
房间注册表中，然后最多检查八个槽位。每个槽位重新校验身份，并固定该次检查开始时的
房间注册表及队伍记录；发生切换时不处理新上下文。已有对象不重复登记，本地角色仍走原处理器。
这不是定时器、复活重放或无限重试，仍需确认真实客户端通知时序是否满足触发条件。

成员 UID 只用于队伍槽位身份校验。登记 key 使用与原生通知 120 相同的
`296aa30(actor)` 计算，不能直接传成员 UID；该函数存在模式与槽位计算分支，零值也可合法。
补登记后直接返回，因此没有重放原处理器的后续位置及状态初始化；这些行为须随画面一起实测。

补丁占用 `.gld127` 的经检查未使用 RX 填充和 `.a4rw` 的经检查未使用 RW 填充；
不增加 PE 节，不移动既有节、不改变入口、通知工具或其它补丁。
RW 区只有九个定长诊断数值，地址 `6eb0100`：尝试、回退、符合队伍条件、已有登记、
登记成功、登记失败、最后 UID、最后槽位、本地就绪检查次数。没有后台线程、文件写入或网络发送。

`verify_candidate.py` 的 48 个用例执行真实候选指令、原生成员查询及原生角色编号函数，
覆盖所有四人有向队友槽位、重复通知及空对象、城镇、旧队伍、错误身份、
已退休对象和其它房间对象等拒绝边界；最终登记调用和 getter 返回使用明确 fixture。
字节差异白名单、PE 校验和、寄存器/栈及不直接写角色资料同时检查。
编号叶子 getter 与模式选择是显式夹具；编号不同于成员 UID 的负测拒绝旧候选，
原生槽位计算及合法零值另有覆盖。
四种本地槽位均覆盖“队友通知早到、本地随后就绪、再次本地通知”的时序；检查期间
换房/换队的夹具保持新上下文其他条件有效，验证不跨上下文登记。旧 v3 在时序用例中失败。

此前旧候选的本机私密取证使用只读进程页的副本，在 Unicorn 中执行真实 getter 和原生登记前半段，
