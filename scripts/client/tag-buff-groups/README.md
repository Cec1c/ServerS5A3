# 帝国竞技场双角色 Buff 两组登记候选

帝国竞技场原1393正文只发送最后编辑的兼容 `Skill/Slots`。两组登记仍在数据库中，
但勇气祝福14在另一组时不会下发。配对候选每个角色按group0、group1发送，
count为4，角色字节为 `nativeRole | (group << 7)`；角色位置仍只有0、1。
每条skill/count/完整119字节物品及可选扩展块格式保持。

客户端先掩去角色字节高位，再查原角色对象；group0保留原两次清除，group1追加，
selection与row调用使用各自组号。角色字节保留在原局部变量中，函数栈分配、
异常处理记录、cookie和SEH处理器逐字保持。每角色必须先group0再group1，
包括空组；不支持仅重发group1或任意颠倒组顺序。两名角色的先后顺序可以交换。

当前固定输入为现网 V215 EXE SHA256
`28e04d1d1c148c841318d533ed8ccb3e426ba5a5f24328b3c913b81303b12a84`。
对应候选为
`40657c19955dc2f594fc2221ef91044170d86406ba6fd193cdb1839877f28cb0`（112816128字节）。
同时保留历史64028352输入→702aa58f输出的精确重建能力；历史候选不能覆盖现网V215。
`build_candidate.py` 只接受这两份固定输入，在已验证空的RX尾部放四段辅助代码，
限制五处hook、section virtual-size与checksum变化；无安装、无启动游戏。

公开服务端限official-24.9，要求 `DNFBRIDGE_BUFF_GROUP_SYNC` 与独立的 `DNFBRIDGE_TAG_BUFF_GROUP_SYNC` 均开启；后者默认关闭。
该开关已有其他双组用途，**开关存在不能证明客户端具备本次1393能力**。
旧EXE不能接收带高位的新正文，正式累计交付必须先封存并验证服务端和此EXE配对，
通过既有签名资源和强制版本准入交付。不能单独部署服务端，也不能把本目录当发布入口。
新客户端接收旧count2、未标记角色字节时保留旧group0行为。

服务端group0读取先保留原完整兼容视图的实例身份迁移，再读两组投影；
不让裁剪后的单组状态获得写权限。group1始终只读。两组来源分别复核，
原来的最后编辑顺序不改变最终四条正文。对历史身份迁移的保持范围是既有活动兼容视图，
不是新增所有非活动历史技能树的迁移。

验证边界：Linux验证双角色来源、历史唯一装备迁移及新增同模板装备、初始歧义拒绝、
空组、编辑顺序、登记漂移、旧格式与相邻帝国入场/切换/结算路径。
`test_native.py`执行42个真实hook/原续接指令的ABI用例，manager leaves为夹具。
`test_parser.py`执行6组零物品完整1393循环、真实selection setter及原SEH cookie读取，
packet I/O、角色表、分配器、map查找/清理和UI为夹具；不执行真实异常展开。
Windows映像验证使用SEC_IMAGE_NO_EXECUTE，不启动游戏。
V215新基线重跑上述42+6用例通过，所有改动外字节保持；保留现网黑钻等更新。
真实装备数值的原生复制、登记装备选择及勇气取值链已另有16例通过，
其解析、容器存储及场景边界为夹具，不等于1393到完整施放或GUI验收。
