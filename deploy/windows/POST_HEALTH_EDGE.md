# 发布后健康证明共享时限与重准备

发布部署在游戏进程健康后读取一次新的资源边缘快照。挑战包含随机 nonce、运行 ID、
源码提交、服务端摘要、镜像摘要、健康前快照摘要和请求时间。响应必须携带完全相同的
挑战，且快照采集时间不得早于请求时间。发布状态、管理状态和配置摘要在健康前后必须
一致，其他字段均不进入日志或回执正文。

## 时限

一次交换使用 100 秒总预算。独立资源快照最多 60 秒，两次时钟读取各最多 20 秒，必要时
的一次时钟等待最多 30 秒，响应投递最多 20 秒。远端等待为 120 秒，因此本地操作始终为
响应接收和校验保留 20 秒。预算耗尽后不会再启动新操作。

## 诊断和重准备

本地每次交换写入 `post-health-edge-diagnostics.json`，包含总预算、总耗时、最终状态，
以及各阶段的规定时限、实际耗时、成功或失败状态和异常类型。远端失败写入
`post-health-edge-error.json`，只记录挑战 nonce、请求时间和异常类型。

请求文件和响应文件都采用一次性写入。已有请求、已有响应、链接、重复响应或超限响应
都会失败。交换失败停留在原 deploy 的 `try/except` 内，由既有回退路径恢复旧进程和配置，
不会终止、重试或重放当前远端进程。再次部署必须使用新的运行 ID，重新执行 prepare、
generate 和 deploy，旧挑战和旧响应不会被复用。

## 接入位置

`deploy/remote/game_update.py` 在既有 `edge-snapshot` 和 `checked_edge_evidence` 之后
提供 `checked_post_health_edge` 与 `await_post_health_edge`。挑战只在完成重启、容器健康、
进程摘要、通道和配置校验后发出，并在写入部署回执前完成。`edge()` 在交换成功后改用
刚验证的新快照，后续发布检查无需依赖已经超过 300 秒的启动前快照。

`deploy/windows/game_update.py` 的 `Update.ssh` 接受可选超时，deploy 使用同一 SSH 进程
读取挑战、执行交换并继续读取原进程输出。远端进程若没有挑战前缀和等待函数，Windows
端自动使用原有 SSH 路径。

## 历史准备兼容

已经处于 prepare 或 generate 阶段的历史运行不需要重建。Windows 端会根据实际发送的
worker 字节检测交换能力，缺少挑战实现的旧 worker 继续走原路径。具备交换能力的 worker
仍只操作原有运行目录，健康前快照、准备镜像、服务端摘要和通道信息均按原回执读取。
历史运行目录中没有交换文件时会新建一次请求。已存在的请求或响应会被视为重放并失败。

## 验证

```text
python -m unittest deploy/windows/test_post_health_exchange_budget.py
```

测试夹具直接加载公开的 `deploy/remote/game_update.py` 和
`deploy/windows/game_update.py`，覆盖慢快照、总预算、投递预留、预算耗尽、时钟等待、
阶段诊断、敏感信息排除、单进程回退、一次性挑战、健康前后状态变化、重复交换拒绝、
超时、SSH 超时传递、当前远端选择交换入口，以及历史 worker 回退。

本组包含 19 项测试，其中一个用例启动真实子进程，让 Windows 收包入口与远端等待函数
完成同一次交换。
